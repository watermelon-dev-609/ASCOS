# 质量门禁与 CTO 最终检查

## 质量门禁（Quality Gate）
在交付前阻断**严重缺陷**；非严重瑕疵记为风险，避免过度迭代。

门禁清单：
- [ ] 安全：鉴权 / 授权 / 注入 / XSS / 越权 / 脱敏 已检查
- [ ] 输入：所有外部输入已校验
- [ ] 契约：接口与错误码符合统一规范
- [ ] 可靠性：幂等 / 事务 / 竞态已处理（如适用）
- [ ] 测试：正常 / 边界 / 异常覆盖，关键路径通过
- [ ] 资源：前端资源释放、后端连接 / 句柄释放
- [ ] 配置：无硬编码密钥，敏感项走环境变量
- [ ] 文档：关键逻辑有注释，变更有说明

出现以下任一项 → 阻断：未鉴权的敏感操作、SQL 注入风险、硬编码密钥、无测试的核心逻辑、越权风险。

## CTO 最终检查
交付前确认：
- 目标是否达成（用户真实意图，而非字面请求）
- 是否有重大需求缺失
- 架构是否适度（无过度设计）
- 安全模型是否成立
- 测试是否覆盖有意义的行为
- 部署 / 运维是否可行

## 交付输出
- 产物（代码 / 文档 / 链接）
- 关键决策简述（为何这样选）
- **剩余风险清单**：主动暴露未覆盖的薄弱处（越权、注入、竞态、数据泄露、依赖风险等）

## 完成定义（DoD）联动
质量门禁判定「能否放行」，DoD（`definition-of-done.md`）定义「是否真正做完」。放行前确认 DoD 全部满足：实现、验证（Build/Test/Lint/Type Check 真实证据）、关键测试、Code Review、安全与权限检查、风险清单、必要文档更新。

## 完成前验证联动
门禁前必须经过 `verification.md`：用 Build/Test/Lint/Type Check 的真实结果作为证据；无证据不得声称完成。

## 发布检查联动
涉及上线时，门禁还需确认 `release.md` 的迁移可回滚、向后兼容、回滚方案、上线后健康检查。

## 反模式
- **禁止使用虚构分数作为完成条件（见 `references/non-negotiables.md` 第 1 条）。**
- 不因非严重瑕疵无限迭代；非严重问题记为风险而非阻断。
