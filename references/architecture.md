# 架构与设计规范

## 设计原则
- 高内聚、低耦合；单一职责（SRP）。
- KISS / DRY / YAGNI：简单优先，不为未来臆想的需求提前抽象。
- 接口契约先行：先定义接口与数据结构，再实现。
- 分层架构（如 controller / service / repository），业务逻辑与 IO（DB / 网络 / 文件）分离，业务逻辑不依赖具体存储。
- 统一错误码契约（前后端共用）：`{ ok, code, msg, data }`。

## 技术决策（Decision Engine）
遇到以下权衡，默认选更简单的一侧，除非需求明确要求：
- 单体 vs 服务拆分 → 单体优先，拆分需有清晰边界与运维收益。
- 同步 vs 异步 → 同步优先，异步仅在真正需要解耦 / 削峰时。
- SQL vs NoSQL → 关系型优先，除非有强理由（文档 / 图 / 海量 KV）。
- 缓存 vs 直查 → 直查优先，缓存仅在实测瓶颈后引入。
- 自建 vs 库 / 框架 → 优先成熟库，避免重复造轮子。

## 反过度设计
- 不轻易引入：消息队列、Redis、微服务、K8s、事件溯源、向量库、额外 Agent。
- 若引入任何基础设施，必须在交付中写明：**收益**（解决什么具体问题）+ **成本**（运维、复杂度、学习曲线）。

## 架构决策记录
重大架构选择用 `templates/ADR.md` 记录：背景、决策、备选、后果。

## 文档连续性
ADR 是文档链路的一环：PRD（需求源）→ ADR（关键决策）→ API_SPEC（接口）→ TEST_PLAN（验收与风险）。需求变更时同步更新下游，详见 `artifact-continuity.md`。

## 技术事实新鲜度
对版本、API 行为、弃用项、安全方案等易变事实，先查官方文档 / RFC / Release Notes 再决策，详见 `research-freshness.md`。不凭记忆下结论。

## 技术栈适配（原则优先于模式）
本章的 controller/service/repository、SQL 优先、`{ ok, code, msg, data }` 等是 **Web 后台的原则性示范**。应用到 CLI、数据管道、ML、移动端、嵌入式等其他技术栈时：
- **保留原则**：契约先行、输入校验、业务 / IO 分离、统一错误表达、可观测、测试三场景（正常 / 边界 / 异常）。
- **不必照搬具体模式**：按实际栈选择对应结构与错误表达（如 CLI 用退出码 + stderr，而非 HTTP 风格错误码）。
- 反过度设计立场不变：不因为「企业级」就给非 Web 场景硬套 Web 分层。
