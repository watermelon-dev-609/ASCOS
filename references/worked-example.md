# 实战样例：从一句话需求到交付

> 目的：给宿主 Agent 一个可对照的范本，理解本 Skill 各阶段的**产出形态**与**尺度**。
> 示例任务：**「帮我做个登录功能」**（中任务，已有 Web 项目）。

---

## 第 1 步 · 代码库感知（仅已有项目）
- 技术栈：Next.js + Prisma + PostgreSQL，已有 `lib/auth.ts`（JWT，无刷新令牌）。
- 既有能力：用户表含 `email / passwordHash`；注册接口已存在。
- **复用点**：直接扩展 `lib/auth.ts`，不另起炉灶（避免重复造轮子）。

## 第 2–5 步 · 补全需求（用户只说一点，不代表只有一点）
主动补全、不狂问；把假设显式标注：
- 登录方式：邮箱 + 密码（默认）→ 假设**暂不做**手机号 / 第三方，标注为「假设待确认」。
- 会话：访问令牌 + 刷新令牌？过期策略？（默认 15min + 7d 刷新）
- 安全防护：密码错误限流防爆破、HTTPS（传输层）、XSS / CSRF 防护。
- 失败路径：账号不存在 / 密码错误 / 账号锁定 / Token 过期。
- 权限：登录后角色如何携带——**前端仅展示，后端每次校验**（见 `security.md`）。
- 【安全视角】错误提示不能区分「账号不存在」还是「密码错」，防用户枚举。

## 第 6 步 · 变更影响
- 影响：`lib/auth.ts`、登录路由、用户表（刷新令牌表）、前端登录页、测试用例。
- 兼容性：存量 JWT 用户需平滑过渡（双 token 并存期）。

## 第 7 步 · 选角
架构 + 后端 + 安全 + QA（见 `roles.md`；本任务不涉及前端大改与上线）。

## 第 8–9 步 · 设计与实现（节选）
- 统一错误码：`{ ok:false, code:"AUTH_INVALID", msg:"邮箱或密码错误", data:null }`（不泄露是哪项错误）。
- 防爆破：连续 5 次失败锁 15 分钟 → **反过度设计判断**：先用 DB 计数（低 QPS 足够），标注若上量再迁 Redis 及其收益/成本（见 `architecture.md`）。
- 密码：bcrypt + 恒定时间比较，杜绝时序攻击。

## 第 10–13 步 · 测试 / 安全审查 / Code Review / 验证
- 测试三场景（见 `testing.md`）：正常登录、错误密码、锁定后登录、Token 过期刷新。
- 安全审查：参数化查询（注入）、转义（XSS）、对象级鉴权（越权）、不回显口令（脱敏）。
- 验证证据（真实，非口述）：`npm test auth` 通过、`tsc` 无类型错 → 写入交付说明。

## 第 14–17 步 · 门禁 / CTO / 交付
- 质量门禁：无硬编码密钥（`JWT_SECRET` 走 env）、输入校验齐全 → 放行。
- CTO 检查：目标达成？无重大缺失？架构适度（未过度引入 Redis）？安全成立？可部署？
- **交付形态（中任务）**：实现说明 + 关键决策（为何双 token）+ 测试证据 + **风险清单**：

### 风险清单（必附，见 non-negotiables 第 2 条）
1. 防爆破当前用 DB 计数，高并发下需迁 Redis（已标注收益/成本）。
2. 第三方登录 / 手机号登录未做（假设待确认）。
3. 登录审计日志尚未接入，难追溯暴力尝试来源。
4. 未做 MFA（如后续涉及敏感操作建议补充）。

---

## 这个样例说明了什么
- 用户只说「登录」，Skill 主动补到了限流、防枚举、刷新令牌、权限载体等用户没想到但系统必需的部分。
- 没有把简单登录扩成微服务 / 网关 / 事件总线（反过度设计）。
- 每一步都有明确产物，且**交付带真实验证证据 + 风险清单**，没有用 `90/100` 之类的虚构分数。
