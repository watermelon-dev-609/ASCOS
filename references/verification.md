# 完成前验证（Verification Before Completion）— P0

代码写完 ≠ 任务完成。必须用证据证明改动可用。

## 原则
- 能运行时：执行 Build / Test / Lint / Type Check，用真实结果说话。
- 关键路径必须实际验证，而不是口头判断「应该没问题」。
- 无法验证时（缺环境 / 缺依赖 / 纯设计），必须明确列出未验证项与原因。
- 没有证据时，不得声称「已修复」「已完成」「已通过」。

## 做法
- 优先在受控环境跑命令获取证据（如测试输出、构建日志、类型检查结果）。
- 把关键验证结果（命令 + 结论）写进交付说明。
- 验证失败即回到修复，不强行交付。

## 与流程关系
对应工作流第 13 步，位于 Code Review 之后、质量门禁之前；是质量门禁的重要输入。

## 非代码任务的验证（设计 / PRD / 架构类）
当任务产物是文档或决策而非可运行代码时，无法跑 Build/Test，验证证据改为：
- **需求补全闭环**：列出「用户原话 → 我们补全了什么 → 是否仍有需用户确认项」，证明没漏掉关键隐含需求。
- **决策可追溯**：每个关键选型都能在 ADR / 文档中查到依据与备选方案（见 `architecture.md`）。
- **一致性检查**：PRD → ADR → API_SPEC → TEST_PLAN 链路无矛盾（见 `artifact-continuity.md`）。
- **对抗性反问**：能否举出一个该方案会失败 / 被滥用的具体场景？能举出，说明思考到位。
无上述证据时，不声称「方案已完备」，并显式标注未验证项（见 `non-negotiables.md` 第 2 条）。
