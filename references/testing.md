# 测试规范

## 覆盖三类场景
每个核心逻辑至少覆盖：
1. 正常路径（happy path）
2. 边界（空值、极值、长度上限、首 / 末项）
3. 异常（非法输入、依赖失败、超时、并发冲突）

## 层级
- 单元测试：纯逻辑 / 业务规则，快、独立、可重复。
- 集成测试：接口 / DB / 外部依赖交互。
- 端到端（按需）：关键用户路径。

## 质量
- 测试可独立运行，不依赖共享可变状态；用 mock 隔离外部依赖。
- 失败信息明确（期望 vs 实际）。
- 提交代码时测试通过；CI 中跑测试门禁。

## 计划与执行
- 交付前用 `templates/TEST_PLAN.md` 列出测试范围、用例、环境与通过标准。
- 安全相关功能（登录、权限、支付）必须有针对性测试用例。

## 测试策略分级（按任务风险匹配深度）
不所有任务都用同样重的测试方式，也不只要求「有单元测试」。

- **核心业务**：单元测试 + 集成测试，覆盖关键逻辑与边界。
- **Bug 修复**：优先补**回归测试**，用用例锁定该缺陷防止复发（见 `debugging.md`）。
- **权限 / 安全 / 支付 / 事务**：必须重点测试**异常路径与攻击路径**（越权、注入、并发冲突、重复提交）。
- **普通 UI 微调**：按风险决定测试深度，低风险可仅做冒烟验证。

原则：测试深度与变更风险成正比，避免过度测试拖慢小任务。
