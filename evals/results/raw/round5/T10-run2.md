## 二、需求补全（`requirements` 阶段产出）

### 事实（来自你的原话，非推断）
1. 需要「商品」这一资源的**增、删、改、查**接口。

### 假设（未确认，如无异议我按此执行）
| # | 假设 | 理由 |
|---|---|---|
| A1 | REST + JSON，资源路径 `/api/products`，复用项目现有的统一响应包装与错误码体系 | 业界默认，且与既有资源保持一致的成本最低 |
| A2 | 权限：**读**（列表/详情）登录用户可用，甚至可能公开；**写**（增/改/删）需 `admin`（或 `merchant`）角色 | 商品是主数据，写入必须鉴权；具体角色待确认 |
| A3 | **删除 = 软删除**（`deleted_at` 或 `status=off_shelf`），不提供物理删除接口 | 商品会被订单、购物车、库存引用，物理删除会破坏历史数据外键 |
| A4 | 商品为**单规格**（无独立 SKU 子表） | 最小可用；若有多规格则表结构与接口形态都变，属分叉点 |
| A5 | 列表支持分页（`page`/`pageSize`，默认 20，上限 100）+ `keyword`/`status`/`categoryId` 筛选 | 无分页的列表接口在生产必炸 |
| A6 | 金额以**整数（分）**存储与传输，不用浮点数 | 金额精度事故高发 |
| A7 | 审计字段 `created_by` / `updated_by` / `created_at` / `updated_at` 必带 | 主数据可追溯性 |
| A8 | 服务端校验为准，不信任客户端传入的 `id`、状态与审计字段 | 安全基线 |

### 建议（我推荐，你可以否）
- **S1**：库存 `stock` **不放进通用 update 接口**，改由独立库存流程（下单扣减/入库单）变更，避免并发覆盖；本次 update 只改名称、类目、价格、描述、图片、状态。
- **S2**：上架/下架用 `PATCH /api/products/{id}/status` 独立接口，语义清晰、便于审计，不与 update 混在一起。
- **S3**：`skuCode` 加**唯一索引**（按商家维度唯一），创建时冲突返回 409。
- **S4**：创建接口暂不做 `Idempotency-Key`（无明确重试场景，属过度设计）；如前端有重复提交问题再补。

## 三、接口草案（API_SPEC 草稿，落地前以代码库惯例为准）

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| POST | `/api/products` | 创建商品 | admin/merchant |
| GET | `/api/products` | 分页列表（keyword/status/categoryId） | 登录（或公开，待确认） |
| GET | `/api/products/{id}` | 详情 | 同上 |
| PUT/PATCH | `/api/products/{id}` | 更新（不含库存） | admin/merchant |
| PATCH | `/api/products/{id}/status` | 上架/下架 | admin/merchant |
| DELETE | `/api/products/{id}` | **软删除**（下线） | admin/merchant |

**字段草案**：`id`、`name`(必填, ≤120)、`categoryId`(必填, 外键存在性校验)、`skuCode`(唯一)、`priceCents`(必填, ≥0 整数)、`stock`(只读/由库存流程维护)、`status`(`draft|on_sale|off_sale`)、`description`、`images`(数组, 限张数)、`createdBy/updatedBy/createdAt/updatedAt`、`deletedAt`。

**错误码**：400 参数校验失败 / 401 未登录 / 403 越权 / 404 不存在或已删除 / 409 `skuCode` 冲突 / 422 业务规则拒绝（如类目不存在）。

**幂等与并发**：更新用乐观锁（`version` 或 `updatedAt` 比对），冲突返回 409；删除/下架幂等（重复调用返回成功或 404，二选一并全程一致）。

## 四、需要你确认的阻断项（3 条，其余按假设自行推进）

1. **权限模型**：谁能写？`admin` 全量，还是按商家/店铺隔离（`merchant` 只能改自己的商品）？→ 决定是否引入数据行级归属字段（多租户分叉点）。
2. **是否有多规格 SKU**：有 SKU 则需 `product` + `sku` 两张表、价格/库存下沉到 SKU，接口形态完全不同。
3. **删除语义与流程**：软删除即终态，还是需要「草稿 → 待审核 → 上架」状态机、以及是否允许彻底物理删除（含 GDPR/合规诉求）？

> 这 3 条会改变数据模型与接口边界，属「需求不足以定边界」；在你回复前，我按 A3/A4 + admin 单角色推进，并在代码里把这三处留成明确的扩展 seam，不写死。

不属于必须询问：无破坏性操作、无计费、无对外发消息、无需你提供密钥（凭证一律走环境变量）。

## 五、确认后的执行计划（`implementation` → `code-review` → `verification`）

1. **感知代码库**：定位现有 Controller / Service / Repository 分层、统一响应与异常中间件、迁移脚本目录，找一个「已存在的同类资源」照抄其模式（优先复用，不另起炉灶）。
2. **数据层**：迁移脚本建表 + 索引（`sku_code` 唯一、`category_id`、`status`、软删过滤）+ 模型定义。
3. **校验层**：DTO/schema 层字段校验（长度、范围、枚举、外键存在性）。
4. **服务层**：CRUD 逻辑、事务边界、软删过滤、乐观锁、审计字段注入。
5. **接口层**：路由 + 鉴权中间件 + 参数绑定；`stock` 不进 update。
6. **测试（`testing.md`）**：
   - 单测：service 层（创建/更新/软删/唯一冲突/越权）
   - 集成：5 个接口各 1 个 Happy Path + 401/403 + 400 校验 + 404（软删后不可见）+ 409 冲突
   - 回归：受影响的订单/购物车/库存相关既有用例全跑
7. **`code-review`**：双轴报告（Standards：安全/校验/事务/命名；Spec：与本草案逐条对齐），基点 = 需求确认前的 HEAD。
8. **`verification`**：DoD 逐项判定 —— Build ✅ / Test ✅ / Lint ✅ / Type Check ✅ **必须给出真实命令输出**；任一缺失即判定「未完成」，不得声称通过。
