## 4. 你确认后的执行计划（预览）

### 阶段 1 — `architecture`（产出：模块与接口设计 + 变更影响清单 + ADR）

1. **现状盘点**：模块清单、依赖图、识别出环、共享可变状态、上帝对象、跨层直连。
2. **行为冻结基线**：先补齐关键路径测试 + 类型/构建门禁，作为后续重构的红绿护栏。没有这步，拆分不可验证。
3. **划边界**：按业务能力切分，遵循深模块原则（接口窄、实现厚）；明确每模块的**公开接口 / 私有实现 / 禁止被谁依赖**。
4. **定依赖方向**：单向依赖，禁止环；跨模块只能走显式接口，禁止直连他人数据表与私有模块。
5. **ADR**：记录"为什么这样切、为什么不拆成微服务、未来物理拆分的触发条件"。
6. **变更影响清单**：逐文件列出移动/改名/导入路径变更，以及受影响的测试、配置、脚本、CI。

### 阶段 2 — `implementation`（产出：可运行代码 + 测试 + 验证命令）

采用 **Strangler Fig（绞杀者）** 式增量搬运，而不是一次性大搬家：

- 每一步只做一件事：**先加新边界 → 加适配层 → 切调用方 → 删旧实现**。
- 每步都是一次可独立合入、可独立回滚的提交；禁止"搬运 + 改逻辑"混在一个 diff 里。
- 每步跑 build / test / lint / typecheck，拿到**真实证据**（不是"应该没问题"）。
- 若某处无法在确认的 seam 上测试 → 明确写出来，记为风险，不静默跳过。

### 阶段 3 — `verification`（产出：DoD 逐项结论 + 质量门禁 + 剩余风险清单）

- DoD 逐项判定（不打分、不用"90/100"这类虚构分数）：
  - [ ] 全部 build / test / lint / typecheck 通过（附命令与输出证据）
  - [ ] 模块间无循环依赖（可用工具或脚本证明）
  - [ ] 跨模块不存在直连他人数据表 / 私有实现的情况
  - [ ] 重构前后行为一致（基线测试全绿；关键路径有对照验证）
  - [ ] ADR 与变更影响清单齐备，且与实际实现一致
  - [ ] 回滚路径验证过（至少演练到可执行的程度）
  - [ ] 若触及鉴权 / 对外接口 / 数据迁移 → 安全审查通过
- 交付：产物 + 关键决策 + **剩余风险清单**（见第 6 节）。

**假设（待你确认，不是结论）**
- 假设当前是单进程单体、单库共享表。
- 假设现有测试覆盖不足以支撑大规模搬运（多数"乱掉的单体"都是这个情况）。
- 假设目标是提升可维护性，而非解决性能/容量问题。

**建议**

- 先立护栏（测试 + 门禁）再搬家。顺序反了，重构无法验证。
