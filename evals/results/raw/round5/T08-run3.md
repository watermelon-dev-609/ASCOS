# 代码审查 — 结论：**暂不启动，缺输入（阻断）**

按总控路由表归类：用户意图 = 「只要求代码审查」→ 调用链 `code-review` → `verification`。
但 `code-review` 的入口契约是 **diff + 基点（base）**，这两项当前都不可得，按契约必须**立即报错、不得静默降级**（`SKILL.md` 第 86 行：基点不可解析或 diff 为空 → 立即报错）。

## 一、为什么现在不能给审查结论

| 契约要求 | 当前状态 | 说明 |
|---|---|---|
| diff（改了什么） | ❌ 未提供 | 「这次的改动」没有指向任何 commit / PR / 文件集合 |
| 基点（和谁比） | ❌ 未提供 | 无 base branch 或 base commit，无法判定「新增」与「既有」 |
| 代码库上下文（`CONTEXT.md`） | ❌ 本轮不可读 | 强制前置：已有代码库任务须先消费 `references/repository-awareness.md` + `CONTEXT.md`，本轮未加载，术语与既有约束无法对齐 |
| 验收标准 / 需求基线 | ❌ 未提供 | Spec 轴审查需要「改完应该是什么样」的参照物 |

**事实 / 假设 / 建议分离**：以上是**事实**（输入缺失）；下文「我会怎么查」是**计划**，不是已执行的结论。我不会凭猜测列出「发现的问题」——那会把假设伪装成事实。

## 二、需要你提供的东西（最小集，任一项缺失都会让某一轴审查失效）

1. **diff 来源**（三选一即可）
   - commit 区间：`git diff <base>..<head>` 或 `git log -p` 输出
   - PR / MR 编号或链接
   - 直接贴改动文件路径清单 + 关键片段
2. **基点**：base 分支名（如 `main`）或 base commit SHA。
3. **改动意图**：这一版要解决的原始需求 / Issue 描述，或一句话「改完应该满足什么」——没有它，Spec 轴只能做静态规范检查，无法判断「是否解决了真正的问题」。
4. **验证证据**（若已有）：Build / Test / Lint / Type Check 的真实输出。

> 补充：若改动涉及**登录 / 权限 / 支付 / 对外接口 / 数据迁移 / 敏感数据**，请显式说明。按分级表这会把任务**至少抬到中级**并强制走 `references/security.md` 安全审查；上线场景还要叠加 `release` + `observability`。

## 三、拿到输入后我会执行的审查（双轴）

**Standards 轴（工程规范，与需求无关）**
- 安全与鉴权：越权路径、输入校验、敏感数据落库/落日志、密钥是否走环境变量
- 数据完整性：并发、事务边界、幂等、失败回滚、迁移的向前/向后兼容
- 错误处理与可观测性：异常是否被吞、日志是否带 trace 上下文、关键路径是否有指标
- 变更影响面：改这一处会波及哪些调用方（`references/change-impact.md`）
- 测试：新增/修改逻辑是否有覆盖，边界与异常分支是否被测
- 复杂度：是否存在可删的过度设计（反过度设计原则）

**Spec 轴（是否达成预期行为）**
- 逐条对齐你给的验收标准
- 边界条件、异常流、权限矩阵是否按预期
- 与既有代码约定的一致性（命名、分层、复用既有工具而非另起一套）

**输出格式**：按 阻断（Blocker）/ 建议（Should）/ 可选（Nit） 三级列出，每条给出 `文件:行号`、问题、原因、建议改法；随后 `verification` 做 DoD 逐项判定并附**剩余风险清单**。
