## 2. 需求补全

用户原话只有一句「加个登录功能」。按「主动补全，而非狂问」原则，能合理推断的我自己补，只有真正分叉的地方才问。

### 事实（Fact）
- 需求：为现有项目增加登录能力。
- 项目已存在（非从零搭建），是既有代码库。
- 含鉴权要素 → 触发强制安全审查。

### 假设（Assumption，**均未经代码库验证**，感知后需修正）
- A1：项目是 Web 应用，存在前后端分离的登录页或需要新增登录页。
- A2：目前**没有任何**登录/会话机制（若已有，任务性质会变成「增强现有鉴权」而非「新建」，链路与风险完全不同）。
- A3：单租户，不需要企业级 SSO / 多组织隔离。
- A4：用户量级小到中等，不需要为登录引入 Redis、MQ 等新基础设施（反过度设计原则）。

### 建议（Recommendation，非事实）
- 优先复用项目已有的 Web 框架官方/社区主流认证方案，**不手写密码学、不自己设计令牌格式**。
- 密码存储用成熟的自适应哈希（bcrypt / Argon2id），禁止 MD5/SHA 系列裸哈希，禁止可逆加密存密码。
- 会话 Cookie：`HttpOnly` + `Secure` + `SameSite`，并设置合理过期。
- 登录接口必须有失败限流/锁定策略，防暴力破解与撞库。
- 登录失败提示统一（不区分「用户不存在」与「密码错误」，避免账号枚举）。
- 日志/埋点**绝不记录**明文口令、令牌、完整 Cookie。
- 所有关键路径加可观测性：登录成功率、失败原因分布、异常峰值告警。

## 3. 阻断性待确认清单（回答后即可开工）

> 每个问题都给了我的默认建议。**如果你只回一句「按默认来」，我就直接按默认执行，不再追问。**

1. **认证方式**：自建账号密码 / 第三方 OAuth（微信、GitHub、企业微信）/ 企业 SSO（OIDC·SAML）/ 组合？
   - 默认：自建账号密码，暂不接第三方。
   - 注意：接第三方需要你提供 Client ID/Secret，按纪律**只走环境变量**，我不会索要明文口令，也不要把密钥贴进对话。

2. **账号从哪来**：是否同时要注册、邮箱/短信验证、找回密码、2FA/MFA？还是先由管理员在后台建号？
   - 默认：本轮只做**登录**（含登出），注册/找回密码/2FA 不在本轮范围，但接口与数据模型预留扩展位。

3. **会话机制**：服务端 Session + Cookie / 无状态 JWT / 框架自带会话？
   - 默认：**优先沿用项目现有框架的官方会话方案**；只有在存在明确的跨域/多服务消费场景时才考虑 JWT（JWT 的吊销复杂度是真实成本，不默认引入）。

4. **权限模型**：登录后是否立刻需要角色/权限（如 admin vs 普通用户）？还是本轮只做「已登录 / 未登录」二态？
   - 默认：本轮只做二态鉴权，但用户表预留角色字段，避免之后迁移。
   - 这是架构分叉点，按纪律**大任务必须确认**。

5. **登录后的边界**：哪些页面/接口需要登录才能访问？是否有必须保持公开的路径（首页、健康检查、静态资源、回调）？未登录时是跳登录页还是返回 401？
   - 默认：白名单默认放行（首页、静态资源、健康检查、登录接口本身），其余需登录；页面跳登录页，API 返回 401。

6. **技术栈确认（解除第 1 节阻塞）**：请告诉我或授权我读取代码库——前端框架、后端语言/框架、数据库、是否已有用户表/会话中间件。

## 4. 确认后的执行计划

1. **感知**：读 `repository-awareness.md` + `CONTEXT.md`，产出术语对齐与既有能力清单（是否有可复用的用户/会话设施）。
2. **架构**：模块与接口设计 + **变更影响清单**（登录会影响路由、中间件、数据模型、前端导航、现有接口的鉴权假设）+ 如需则出 ADR；同时读 `references/security.md` 做安全设计。
3. **实现**：按 seam 写码 + 测试（成功登录、错误口令、账号不存在、暴力破解限流、会话过期、越权访问、未登录重定向）。
4. **验证**：Build / Test / Lint / Type Check **真实执行并贴出证据**，逐项判定 DoD；无真实验证证据即判未完成，不会声称通过。
