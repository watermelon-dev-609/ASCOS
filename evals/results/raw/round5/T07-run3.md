### 1.3 验收标准（Given / When / Then，可测）

1. **分页**：100 条数据，`pageSize=20` → 返回 20 条、5 页、`total=100`；逐页遍历 5 页，去重后恰好 100 条（验证无重复无遗漏）。
2. **边界**：`page=0` / `page=-1` → 归一为第 1 页；`page=9999` → 空列表不报错；`pageSize=0` → 取默认值；`pageSize=100000` → 截断为 100；`pageSize=abc` → 400。
3. **搜索**：关键字命中订单号 / 客户名 / 手机号时结果正确；结果集同样受分页约束。
4. **空关键字**：`keyword` 为空或全空白 → 等价于不筛选，不拼入 `WHERE`。
5. **特殊字符**：关键字含 `%` `_` `'` `"` `<` 及 emoji → 不报错、不报错 SQL、按字面量匹配、`'` 不引发注入。
6. **超长**：`keyword` 长度 > 64 → 400 或截断（二选一，须一致），不得把超长串打到 DB。
7. **权限**：A 用户的关键字搜索结果中不出现 B 用户的订单（越权用例，自动化断言）。
8. **前端**：连续快速输入只触发末次请求；翻页时 `page` 与 `keyword` 同时保留；刷新后状态还原。
9. **性能**：在约定数据量下（见 §6 待确认项 3）P95 列表接口延迟满足阈值，并给出 `EXPLAIN` 证据。

## 2. 实现方案（`implementation`）

### 2.1 接口契约（待与真实栈对齐）

```
GET /api/orders?page=1&pageSize=20&keyword=xxx&sort=createdAt:desc

200 {
  "items": [ { "id", "orderNo", "customerName", "phone", "amount", "status", "createdAt" } ],
  "total": 137,
  "page": 1,
  "pageSize": 20,
  "hasMore": true
}
400 { "code": "INVALID_PARAM", "message": "..." }
```

原则：`page/pageSize/keyword/sort` 全部走**白名单校验 + 参数化查询**，禁止字符串拼接 SQL。

### 2.2 后端要点

1. **参数校验**（边界处，唯一需要防御的地方）
   - `page`：整数 ≥ 1，非法/缺失 → 1
   - `pageSize`：整数 1–100，非法/缺失 → 20，超上限 → 100
   - `sort`：白名单枚举（如 `createdAt:desc|createdAt:asc|amount:desc`），非法 → 默认
   - `keyword`：trim，长度 ≤ 64，空串视为无筛选
2. **查询构造**
   - 归属条件**无条件**拼入：`WHERE tenant_id = ? AND ...`（不能被 keyword 分支绕过）
   - 关键字：`AND (order_no LIKE ? ESCAPE '\' OR customer_name LIKE ? ESCAPE '\' OR phone LIKE ? ESCAPE '\')`，占位符传参，转义 `% _ \`
   - 手机号归一化后再匹配（去空格 / `-` / `(` `)`）
   - 排序：`ORDER BY created_at DESC, id DESC`（**必须有 tie-breaker**）
3. **计数**：`COUNT(*)` 与列表共用同一 `WHERE`；`total` 与 `items` 必须在同一事务快照内，避免翻页时总数漂移导致尾页空。
4. **N+1**：列表若带关联数据（客户、商品），用一次性批量查询或 join，禁止逐行查。
5. **索引**：搜索字段按选择性建索引；`ORDER BY` 字段建索引（`created_at, id` 复合）。

### 2.3 前端要点

- 关键字输入防抖 300ms；搜索条件变化时**重置为第 1 页**（常见漏项）。
- 请求竞态：用请求序号或 `AbortController` 丢弃过期响应，避免旧请求覆盖新结果。
- 状态机：`idle / loading / success / empty / error`，错误态可重试。
- 分页器在 `hasMore=false` 或单页时按约定隐藏/禁用。
- `page`、`keyword` 同步到 URL query，刷新可还原。

### 2.4 测试清单（红 → 绿）

- 单测：参数归一化（各非法输入分支）、`LIKE` 转义函数、SQL 构造（断言参数化而非拼接）
- 集成：分页不重不漏（遍历全量比对）、搜索命中、越权隔离、特殊字符不报错
- 前端：防抖只发一次、条件变更重置页码、竞态下展示最新结果

## 5. 剩余风险清单（必附）

| # | 风险 | 影响 | 建议处置 |
|---|---|---|---|
| R1 | 关键字匹配字段未定 | 直接决定索引与 SQL，改动成本高 | **先确认再动手**（§6 Q1） |
| R2 | 数据规模未知 | 决定 `%kw%` 是否可行、是否需 FULLTEXT/ES | 确认量级后定；本轮**不**引入 ES（反过度设计） |
| R3 | 深翻页性能 | offset 越大越慢，万级以后明显退化 | 先限最大页码或改 keyset 游标（`(created_at, id)`），列为后续项 |
| R4 | `COUNT(*)` 成本 | 大表上精确 total 可能拖垮接口 | 必要时改近似计数或去掉 total 改 `hasMore` |
| R5 | 前导通配符 `LIKE '%x%'` 不走 B-tree | 全表扫描 | 小数据量可接受；量大用 FULLTEXT / 倒排，或用前缀匹配 |
| R6 | 越权越租户读取 | 数据泄露，最高危 | 后端强制归属条件 + 自动化越权断言 |
| R7 | 前端请求竞态 | 旧响应覆盖新结果，用户看到错数据 | 请求序号 / `AbortController` |
| R8 | 搜索条件变更未重置页码 | 停留在第 5 页却看到空列表 | 条件变更强制 `page=1` |
| R9 | 排序不稳定（同 `created_at`） | 翻页重复/漏行 | 追加 `id` 作为 tie-breaker |
| R10 | 本轮未读代码库 | 方案可能与既有分页/查询封装重复 | 落地首步：仓库内检索是否已有分页工具、列表权限拦截器、关键字搜索实现，优先复用 |
| R11 | 导出/打印需求外溢 | 用户可能期望"搜索后导出全部" | 提前确认，避免二次返工 |

## 6. 需要你确认的阻断项（只有这些会改变实现路径）

1. **关键字匹配哪些字段？** 订单号 / 客户名 / 手机号 / 商品名 / 收货地址 —— 选哪些？各用精确还是模糊？
2. **需要跳页还是只上拉加载？** 需要跳到第 N 页 → offset；只上拉 → keyset 游标，性能更好。
3. **订单表当前量级与预期增长？** 决定索引方案与是否要走 FULLTEXT / 搜索引擎。
4. **是否必须显示精确总数 `total`？** 不要 total 可显著降低成本。

以上 4 项不影响的部分（参数校验、转义、越权隔离、排序稳定性、前端状态机）已可直接开工。
