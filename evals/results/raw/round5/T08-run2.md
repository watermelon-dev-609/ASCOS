## 我需要你给的（最小集，三选一）

1. **diff**：`git diff main...HEAD`（或 `git diff <base>...<head>`）的输出，或直接给 patch 文件；
2. **PR / MR 链接**：需包含 base 分支与 head commit；
3. **明确基点 + 改动范围**：例如「基于 `origin/main`，改动集中在 `apps/api/src/order/`」。

顺带三个会直接改变审查结论的问题（答不了我就按默认处理，并在报告里显式标为「假设」）：

- **基点是哪个分支 / 哪个 commit？**（没有基点 = 无法判断"这次改了什么"）
- **这次改动的验收标准是什么？** 没有的话我只做 Standards 单轴，Spec 轴结论会明确写「无法判定」，不会假装评了。
- **是否已跑过 Build / Test / Lint / Type Check？** 请把真实命令和输出贴给我。核心信念第 6 条：写完 ≠ 完成，必须有真实验证证据；没有证据的东西我不会写成"已验证"。

## 拿到 diff 后我会产出什么

**双轴报告（Standards / Spec）**

- **Standards 轴**：安全（注入 / 越权 / 敏感数据 / 入口校验）、鉴权与权限模型、错误处理与失败模式、数据完整性与并发、可观测性（日志 / 指标 / 链路）、性能（N+1、无界查询、请求放大、锁范围）、测试覆盖、与既有工程规范的一致性
- **Spec 轴**：改动是否真的满足本次需求与验收标准；是否夹带了范围外的行为变更（scope creep）
- 每条问题按 `文件:行号` 定位，标注 **阻塞 / 建议 / 可选** 三档，并给出**最小修复方向**（不是重写建议）
- **事实 / 假设 / 建议分开标注**；不使用任何形式的虚构分数（不会给你「85/100」这种东西）

之后交给 `verification`：DoD 逐项判定 + 质量门禁 + **剩余风险清单**（必附，这是不可妥协项）。

## 你现在可以先自查的 8 项（不需要我介入）

1. 权限校验是否落在**服务端**，且覆盖「越权访问他人资源」（不只是"登录了就能看"）
2. 所有外部输入是否都有校验，且校验在**入口**，不是只在 UI 层
3. 是否存在 SQL / 命令 / 模板注入面，以及不安全的反序列化
4. 数据库变更是否可回滚、有无锁表风险、是否处理了并发写
5. 错误信息与日志是否泄漏敏感数据（token、手机号、身份证、完整堆栈外抛）
6. 新增代码路径是否有日志与关键指标（否则上线后是黑盒）
7. 是否有 N+1 查询、无界列表查询、请求放大
8. 是否有对应测试（**含一个能复现问题的失败用例**），且 Build / Lint / TypeCheck 真实通过
