# ASCOS 接单：从零搭建一个 SaaS

## 1. 任务判定

| 维度 | 结论 |
|---|---|
| 级别 | **大**（新项目 / 从零搭建：跨层、新架构、含鉴权与订阅计费） |
| 路由 | `requirements` → `architecture` → `implementation`（`verification` 收尾） |
| 强制项 | 命中「鉴权 / 支付 / 对外接口」→ 强制安全审查；若上线另走发布检查 |

## 2. requirements 阶段结论：**失败状态 —— 阻断性业务决策缺失**

按 Skill 契约，`requirements` 的失败状态是「存在阻断性业务决策缺失 → 返回待确认项清单」，且**不得静默降级**。

当前输入「我要做一个 SaaS，帮我从零搭起来」只给出了**交付形态**，没有给出**产品内容**。这不是可以靠推断补齐的空白——SaaS 是外壳，里面装什么决定了数据模型、权限模型、计费模型，三者任一猜错，第一周写下的代码都要推翻。

所以我不往下猜着写脚手架。能合理推断的我已经自己补（见第 4 节），剩下的必须你定。

## 3. P0 待确认项（这 5 项不答，任何设计都是赌）

1. **产品是什么** — 一句话定位（给谁、解决什么、替代现在的什么做法）+ **第一个可付费闭环**的最小场景。没有它，架构无从定边界。
2. **多租户模型**（架构分叉点）— 共享库共享表（`tenant_id` 行级隔离）/ 共享库独立 schema / 独立库。它决定数据归属、隔离强度、成本与后续迁移难度；**后期改这个几乎等于重写**。
3. **权限模型** — 单人使用还是团队邀请协作；RBAC 还是 团队-角色-资源 三层；是否需要 SSO。
4. **计费与身份** — 订阅制 / 按量 / 混合，档位如何；支付渠道（Stripe / 微信支付 / 其他）；身份自建还是托管（Clerk / Supabase Auth / Auth0 / 自研）。**涉及计费与订阅，按纪律我必须停在这里问你，不自行假设。**
5. **交付约束** — 目标用户与合规区域（决定数据 residency 与隐私合规）、上线环境与技术栈偏好、团队规模、是否有既有代码 / 账号 / 域名要复用。

## 4. 我准备直接定的默认值（你不反对就照此执行）

写这些是为了让你**改**，不是展示。全部遵循「反过度设计」：

- **单体优先**：modular monolith（一个可部署单元 + 清晰模块边界）。**默认不引入** 微服务 / K8s / Redis / MQ / 向量库；只有出现真实证据（队列积压、跨模块独立扩缩容需求等）才新增，且我会写明收益与成本。
- **技术栈**：在你答完第 3 节前不锁栈。答完我给 1–2 个候选 + 选型理由 + ADR，而不是现在拍脑袋。
- **工程基线（无论选什么栈都做）**：类型检查 / Lint / 单元+集成测试 / CI / 结构化日志 / 健康检查 / 统一错误码 / 环境变量管理密钥（绝不硬编码，绝不索要明文口令）。
- **安全基线**：所有外部输入校验；**租户隔离在查询层强制**，不依赖「前端没传」；最小权限；审计日志；依赖供应链检查。
- **AI 功能**：当前不预设。后续若需要，单独立项评估，不预先塞向量库。

以上属于**建议/默认值**，不是事实；与你的真实约束冲突时以你的为准。

## 5. 你回答之后的推进节奏

1. `requirements` → PRD + 验收标准 + 风险点（事实 / 假设 / 建议 分标）
2. `architecture` → 模块与接口设计 + 变更影响清单 + ADR（含安全审查结论）
3. `implementation` → TDD 红绿循环，先跑通「注册 → 建租户 → 核心场景 → 计费」的**纵向切片**，而不是横向铺层
4. `verification` → Build / Test / Lint / Type Check 的**真实执行证据** + DoD 逐项判定 + 剩余风险清单
