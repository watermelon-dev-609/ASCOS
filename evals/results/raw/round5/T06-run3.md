## 3. 上报：为什么不停在"直接给你一份新目录结构"

- 拆分的第一性问题不是"文件夹怎么摆"，而是**边界（seam）画在哪**。边界画错，模块化只会把混乱从"文件乱"升级成"模块间循环依赖乱"，比现在的单体更难改。
- 边界只能从**真实调用关系、数据归属、共享状态**里读出来，不能从"清晰的目录名"倒推。
- 因此：**在没有代码库证据前给出的任何模块划分 = 虚构**。（核心信念 #12：事实 / 假设 / 建议分开，不把推断伪装成事实。）

## 4. 需要你确认的清单（阻断性，确认后我才动手）

### 4.1 阻断性业务/技术决策（缺一项就无法定边界）

1. **目标形态分叉（最关键）**
   - A：**模块化单体（modular monolith）** —— 单进程、单部署，内部按领域分模块、强制依赖方向、模块间只走显式接口。
   - B：**物理拆分为多包（monorepo 多 package / 多仓库）** —— 独立构建、独立版本。
   - C：**拆成微服务** —— 独立部署、跨进程通信。
   - 我的**默认建议是 A**（见第 5 节理由），但这是产品形态级分叉，**必须由你拍板**。
2. **本次的完成定义**：是"结构上理清、可维护即可"，还是"必须能独立部署/独立发版"？（决定要不要引入构建与发布链路改造）
3. **能否停机 / 能否接受长分支**：决定走**增量绞杀式迁移（strangler）**还是一次性大搬迁。
4. **回归网是否可信**：现有是否有可跑的测试 / CI？没有的话，拆分前必须先补** characterization test（表征测试）**，否则无法证明"行为未变"——这是重构的安全带，不能跳过。

### 4.2 大任务强制必问的架构分叉点

| 分叉点 | 需要你回答 |
|---|---|
| **数据归属** | 每个模块是否独占自己的表/集合？还是继续共享一个库、靠约定隔离？（共享库时"模块边界"会被 SQL 悄悄击穿） |
| **权限模型** | 鉴权/授权是全局中间件，还是下沉到各模块？模块间调用走什么身份？（影响是否触发强制安全审查） |
| **同步 vs 异步** | 模块间通信：进程内函数调用 / 事件 / 消息队列？（默认建议：先同步接口，事件只在有实际收益时引入） |
| **是否多租户** | 租户维度是否贯穿所有模块？（若单租户，别为"未来可能"提前铺多租户抽象） |

## 5. 我已能给出的默认路线（**假设/建议，非事实**，待代码库证据校正）

**建议：优先做「模块化单体」，不要一上来拆微服务。**

理由（反过度设计，核心信念 #10）：
- 你现在痛点是**可维护性**，不是**伸缩性/独立部署**。模块边界清晰在单体内部就能拿到 80% 收益，成本却是微服务的十分之一。
- 微服务会一次性引入：网络失败、分布式事务、链路追踪、部署编排、跨服务契约版本管理——这些开销在"单体现在很乱"的前提下会把风险放大。
- 模块化单体是**可逆的中间态**：边界稳定、且确实出现独立伸缩/独立发版需求时，再按已验证的 seam 外拆，代价远低于直接从泥球切微服务。

**落地手法（确认后按此执行）**：
1. 先**建边界面**，不搬代码：定义每个模块的公开接口（facade），把跨模块直连改为走接口。
2. 用**依赖方向规则**（如 lint 层依赖约束 / 依赖cruiser 类工具）把"不许反向依赖"变成**机器可校验的门禁**，而不是写在文档里的君子协定。
3. **按依赖倒置的顺序自底向上搬**：先抽无依赖的叶子模块，最后动核心。
4. 每一步都必须**行为不变 + 测试通过**才提交，禁止"边拆边改功能"。
5. 只引入**已证明必要**的新基础设施；任何新增依赖都要写明收益与成本（含供应链审查）。

## 7. DoD（完成定义，逐项判定，不用分数）

- [ ] 模块边界与依赖方向有**文档 + 机器校验**双重约束
- [ ] 无模块间循环依赖（工具可验证）
- [ ] 全部既有测试通过，且迁移期间新增表征测试覆盖被搬动的行为
- [ ] Build / Lint / Type Check 全绿（附真实命令与输出）
- [ ] 对外行为零变更（API 契约、数据 schema 无意外变更）
- [ ] ADR 已记录关键决策与被否决方案
- [ ] 剩余风险清单已交付

## 8. 剩余风险清单（当前已知，随执行更新）

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **未感知代码库即定边界** | 拆出的模块仍与实际耦合不符，返工 | 必须完成 S0 感知与耦合分析后才冻结设计（**当前最高优先级**） |

| R3 | **共享数据库击穿模块边界** | 模块"看起来独立、实际强耦合" | 明确数据归属；跨模块数据访问必须经接口，禁止直连表 |
| R4 | **长分支并行开发冲突** | 合并地狱 | 走增量绞杀 + 小步提交 + 频繁合入主干 |
| R5 | **重构与功能变更混在一起** | 出 Bug 无法定位是迁移还是新逻辑 | 严格执行"迁移期禁止改行为" |
| R6 | 涉及鉴权/权限时未做安全审查 | 越权漏洞 | 若 S0 发现相关代码，强制插入 `security` 审查环节 |
| R7 | **过度拆分** | 模块过碎，跨模块调用成本高于收益 | 遵循"深模块"原则：接口小、实现厚；无明确收益不新增模块 |
| R8 | 引入新依赖（构建/校验/通信） | 供应链与维护成本 | 新增依赖需写明收益与成本，并过供应链审查 |
| R9 | 性能回退（同步调用改层、未来若改异步） | 延迟上升 | 关键路径加基准测试，前后对比 |
