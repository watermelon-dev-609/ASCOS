# 单体拆解为模块化结构 —— 总控路由结论与执行方案

> 说明：本轮我只加载了总控 `SKILL.md`，**尚未扫描你的代码库**。因此下面给的是「路由结论 + 拆分策略 + 必须先确认的分叉点」，而不是一张凭空画出来的新目录树。没有现状事实就给目录结构，是这类任务最常见的返工来源。

## 1. 判断

| 项 | 结论 |
|---|---|
| 意图 | 架构重构 —— 现有单体的模块化拆分 |
| 级别 | **大**（多模块 / 跨层 / 新架构） |
| 强制项 | 涉及跨模块大量改动 → 变更影响清单必做；若拆分触及对外接口或数据迁移，级别只升不降 |

一个前提要先钉死：**「模块清晰」≠「拆微服务」**。单体变乱的根因几乎从不是"没拆成服务"，而是**模块边界缺失 + 依赖方向失控**。在没有独立部署节奏、独立扩容、团队边界这三条硬理由之前，正确解法是**进程内模块化 + 强制依赖规则**，而不是分布式。

## 2. 路由

调用链：`repository-awareness` → `architecture` → `implementation` → `code-review` → `verification`

- **强制前置**（已有代码库）：先读 `references/repository-awareness.md`，消费/生成 `CONTEXT.md`（`references/context-model.md`），产出**变更影响清单**。
- `architecture`：模块划分 + 依赖规则 + 对外接口 + 分阶段迁移路径 + **ADR**（模块边界与依赖方向是长期约束，必须落 ADR）。
- `implementation`：按阶段迁移，行为不变，测试守护。
- `code-review`：双轴（Standards / Spec），重构成果必须过这一道，因为"能跑"掩盖不了"边界被绕过"。
- `verification`：Build / Test / Lint / Type Check 真实证据 + DoD 逐项。
- 按需加载：`change-impact.md`、`testing.md`；若拆分触及数据库 → `database.md`；若触及对外接口/鉴权 → `security.md`。
- 不产出 PRD（这是重构，不是新需求）；**不默认引入 Redis / MQ / K8s / 微服务**。

## 3. 需求补全（事实 / 假设 / 建议分开）

**事实（来自你的原话）**
- 当前是单体；你认为结构混乱；期望结果是模块清晰。

**假设（我推断的，需你确认或推翻）**
- 「乱」的表现是：模块边界不清、存在跨层调用或循环依赖、部分文件过大、改一处牵动多处。
- 你希望**保持单体部署**，只改善内部结构。
- 存在自动化测试，但覆盖不足；重构期间不能长期停需求。

**建议（我的默认策略，若你无异议就按此推进）**
- 绞杀者模式增量迁移，而非大爆炸重写。
- 依赖单向：上层 → 下层；业务模块之间不互相穿透，跨模块只走显式接口。
- 先建边界、再搬代码；先有测试、再动结构。
- 边界用**静态检查规则固化**并进 CI，否则"清晰"撑不过三个月。
- 重构期间不换技术栈、不加中间件，需要的单独走 ADR。

## 4. 必须先确认（阻断性分叉点，不定这些就开工 = 返工）

1. **目标形态**：单体内的模块化（推荐），还是确实要拆独立服务？后者需要给出硬理由（独立部署节奏 / 独立扩容 / 团队边界），否则不做。
2. **业务域清单**：核心业务概念有哪些（如 用户 / 商品 / 库存 / 订单 / 支付 / 营销）。你给，或者授权我先做代码扫描产出候选边界再由你确认。
3. **切分依据**：按业务能力切（推荐，与变更频率对齐）还是按技术层切（controller/service/dao 各一层，治标不治本）。
4. **数据归属**：模块拆开后，表是否要跟着拆/隔离？这是独立的架构决策，可能触发数据迁移，风险等级最高。
5. **是否有对外契约**：有没有外部调用方依赖现有接口/字段？有则重构期间必须保持契约兼容。
6. **现有测试覆盖**：有无自动化测试？没有则**先补 characterization test**（固化现状行为），否则重构就是在赌。
7. **合入方式**：允许小步增量持续合入主干（推荐），还是必须开长生命周期重构分支？

## 5. 执行计划

**阶段 0 —— 现状盘点（先于任何改动，产出事实）**
- 模块依赖图、循环依赖、上帝类/大文件、跨层调用点、重复实现、可测性缺口。
- git 变更热点：改动最频繁的文件 = 最该先有边界的地方。

**阶段 1 —— `architecture`**
- 目标模块划分 + **依赖规则**（谁可以依赖谁，写死）。
- 每个模块的对外接口：深模块原则 —— 接口窄、实现厚。
- 分阶段迁移路径：每一阶段可独立发布、可回滚。
- **变更影响清单**：受影响的文件 / 接口 / 调用方，是否触及 API 契约。
- ADR：模块边界与依赖方向、数据归属决策、是否需要迁移。

**阶段 2 —— `implementation`**
- 按阶段迁移，每阶段**行为不变**，测试守护。
- 命名与术语同步更新到 `CONTEXT.md`。
- 每阶段结束跑 Build / Test / Lint / Type Check。

**阶段 3 —— `code-review` + `verification`**
- 双轴审查：规范符合度 + 是否真的实现了设计意图（重点查边界被绕过、跨模块直连内部实现）。
- 关键业务路径迁移前后行为对比；DoD 逐项判定。

## 6. 验收标准（DoD 草案）

- 无循环依赖；依赖方向可被静态检查验证，并在 CI 中卡死。
- 每个模块有明确对外接口，模块外不得直接访问模块内部实现。
- 迁移前后核心业务路径行为一致（有测试或对比证据，不接受"应该没问题"）。
- 单个模块的改动不再牵动全仓库。
- 每个阶段可独立发布与回滚。

## 7. 剩余风险清单

| 风险 | 说明 | 处置 |
|---|---|---|
| 未看代码先定结构 | 目标结构脱离现实，迁移无法执行 | 阶段 0 现状盘点先行，方案基于事实 |
| 大爆炸式重写 | 长分支、无法回滚、与并行需求冲突 | 绞杀者模式，每阶段可发布可回滚 |
| 测试缺失 | 重构引入的行为变化无法发现 | 先补 characterization test |
| 边界靠自觉 | 三个月后重新变乱 | 依赖规则进 CI 静态检查 |
| 顺手换技术栈 / 加中间件 | 风险与收益不匹配 | 明令禁止，需单独提 ADR |
| 数据归属未决策 | 模块拆了但表还混着，边界形同虚设 | 作为独立架构决策项，必要时走 `database.md` |
| 影响面被低估 | 牵动外部调用方未被识别 | 变更影响清单逐项确认 |
| 进度不可见 | 大重构最容易"做一半" | 分阶段交付，每阶段有可验收产出 |
