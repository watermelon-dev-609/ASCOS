# 关于「整理评审会会议纪要」的回复

这个请求我没有走软件开发总控 Skill，原因和后续处理说明如下。

## 一、未加载 `ai-software-company-skill`

该 Skill 的定位是软件开发交付的编排器，适用范围明确写的是：新功能、页面、API、架构设计、重构、Bug 修复、RAG/AI 功能、部署上线、代码审查等需要产出或改动代码的交付任务。

而它的排除项里同样写明了：**与代码或软件配置无关的纯文案润色、通用知识问答、排期与人员沟通等非软件交付任务**，不适用该 Skill。

把一份评审会记录整理成会议纪要，本质是文档归纳与信息结构化，不涉及任何代码改动、技术方案设计或缺陷修复，因此不属于该 Skill 的路由范围，直接按普通文档任务处理即可。

> 补充一点：即使这份评审会本身是技术评审会（比如方案评审、代码走查），只要本次诉求只是「把记录整理成纪要」，没有要求据此改码、出技术方案或修 Bug，就仍然不触发该 Skill。如果后续你说「按纪要里的结论去改代码 / 修这几个问题」，那时才需要加载 Skill 并路由到 implementation 或 debugging。

## 二、我目前拿不到需要整理的内容

你的描述是「这是今天评审会的记录」，但**实际的记录内容没有随消息一起传过来**——没有附上文本、录音转写、截图，也没有指向某个具体文件。

为了避免凭空编造参会人、议题和结论（会议纪要通常需要归档并对外发出，编造内容的风险很高），我不先给你一版「猜出来的纪要」。请把原始记录贴给我，支持的几种形式：

1. 直接粘贴会议记录的文字（原始流水、聊天记录、转写稿都可以，越原始越完整越好）；
2. 上传记录文件（.md / .txt / .docx / 图片截图）；
3. 告诉我文件在仓库或本地的路径，我去读取；
4. 只有要点口述也可以，我会按纪要格式补结构，但会标注哪些是我补的框架、哪些是你给的事实。

## 四、整理时会遵循的原则

- **不臆造**：参会人、结论、时间点一律以原始记录为准，缺失的标注「待确认」，不自行补全。
- **区分事实与判断**：记录里说了什么 vs 我的归纳，会分开呈现；归纳部分若你不同意可直接删。
- **结论前置**：纪要开头就能看到「通过与否」和「要做什么」，方便不读全文的人快速对齐。
- **待办可执行**：每条 Action 都要有责任人和截止时间，缺的就留空并标红提示你补齐，而不是替你填一个。
- **保留分歧**：评审中的反对意见会保留，不会为了「纪要好看」抹平。
