# 深模块是什么意思？和普通的分层有什么区别？

## 一句话回答

**深模块（Deep Module）** 是 John Ousterhout 在《A Philosophy of Software Design》里提出的概念：一个**接口很小、但实现/功能很丰富**的模块。它用最少的东西让你知道「怎么用」，内部却替你干掉了大量复杂度。

判断标准是**接口复杂度 vs 实现带来的收益**的比值，而不是代码行数。

## 深模块 vs 浅模块

Ousterhout 用「矩形面积」做比喻：模块画成一个矩形，**宽度 = 接口**（要暴露多少东西才用得起来），**深度 = 功能/抽象能力**。

```
  浅模块（Shallow）              深模块（Deep）
┌──────────────────────┐      ┌──────────┐
│ interface 很宽        │      │interface │
│ 一点点功能           │      │  很窄    │
│                      │      │          │
└──────────────────────┘      │  大量    │
                              │  功能    │
                              │          │
                              │          │
                              └──────────┘
```

### 浅模块的典型（反面）

```java
private void addNullValueToAttribute(String attribute) {
    data.put(attribute, null);   // 就干了一行
}
```

这个函数的接口（名字 + 参数）比它的方法体还长。调用者为了用它，得先知道 `attribute` 是什么、`data` 长什么样——**学习成本 > 它省下的成本**，净收益是负的。

类似的还有：
- 只会 `return list.size()` 的 wrapper
- 只有一个实现类、并且永远不会换实现的 `XXXInterface` + `XXXImpl`
- 逐层转发、每层只加一句日志的 Controller → Service → Manager → DAO

### 深模块的典型（正面）

- **Unix 文件 I/O**：`open / read / write / close / lseek` 五个调用，背后藏了磁盘寻址、块缓存、权限校验、文件描述符表、设备驱动……接口极窄，实现极深。
- **Go / Java 的垃圾回收器**：接口是「零」——你什么都不用调用，它自动帮你管内存，内部却极其复杂。
- **SQL 数据库**：一句声明式的 `SELECT`，背后是查询优化、索引选择、事务并发控制。
- **好的 ORM 或 Web 框架**：暴露几个注解/装饰器，吞掉了连接池、映射、路由等一堆脏活。

## 和普通「分层」的区别

这是最容易混淆的地方，核心差异在**目的**：

| | 分层（Layering） | 深模块（Deep Module） |
|---|---|---|
| 关注点 | **依赖方向和职责划分**（谁可以调用谁） | **抽象的质量**（接口的成本 vs 收益） |
| 度量维度 | 纵向：层级、调用链 | 单个模块的「深/浅」 |
| 目的 | 控制依赖、可替换、可测试 | 减少系统总复杂度 |
| 粒度 | 系统级架构决策 | 模块/类级设计判断 |
| 会不会冲突 | 会——分层**常常制造浅模块** | 用来**纠偏**分层的副作用 |

### 关键区别 1：分层不保证抽象，反而容易产出浅模块

标准的 Controller / Service / Repository 三层，很容易退化成：

```java
class UserController { 
    UserService s; 
    public User get(Long id){ return s.get(id); } 
}
class UserService { 
    UserRepo r; 
    public User get(Long id){ return r.get(id); } 
}
class UserRepo { 
    public User get(Long id){ return mapper.selectById(id); } 
}
```

三层干的是同一件事——**透传**。每一层都是一个浅模块：接口（类名 + 方法签名）带来了认知负担，但实现里没有消化任何复杂度。这叫 **pass-through method / pass-through variable**，是分层的典型副作用。

深模块的视角会直接问：**这层消化了什么？** 如果答案是「什么都没消化，只是转发」，那这层就不该存在，或者应该把它和相邻层合并成一个更深的模块。

### 关键区别 2：分层是「怎么摆」，深模块是「值不值」

- 分层回答：**代码放哪里、谁依赖谁**。它关心结构。
- 深模块回答：**这个边界划得划不划算**。它关心性价比。

一个分层架构完全可以是「深」的：比如网络协议栈（物理层 / 链路层 / IP / TCP / 应用），每一层都实实在在地消化了一类复杂度——TCP 消化了丢包重传、乱序重组、拥塞控制，向上提供一个可靠的字节流。这是**分层 + 深模块**的理想组合。

反过来，你可以完全没有分层，但写出很好的深模块；也可以分层分得很规范，却每一层都浅得可怜。

### 关键区别 3：对「拆分」的态度不同

- 分层思维倾向于：**按技术职责切**（表现 / 业务 / 数据）。
- 深模块思维倾向于：**能不切就不切**，切了就必须让每块有足够深度。Ousterhout 甚至说，如果非要拆，宁可**「拆实现、不拆接口」**——把大模块内部拆成若干小文件/小类，但对外的接口仍然只有一个，这样外部看到的是一个深模块，内部实现又不至于臃肿。

## 实践上的判断方法

拿到一个模块（类、函数、服务），问三个问题：

1. **调用者用我需要知道几件事？**（参数个数、配置项、调用顺序、前置条件、需要理解的概念）→ 越少越深。
2. **我替调用者干掉了多少复杂度？**（隐藏了多少细节、决策、边界情况）→ 越多越深。
3. **1 和 2 谁大？** 如果 1 ≥ 2，就是浅模块，考虑合并、删除，或者重新设计让它承担更多责任。

## 一句话总结

> 分层是**关于依赖的结构性约定**，深模块是**关于复杂度的经济性判断**。分层告诉你「往哪儿放」，深模块告诉你「这个边界本身划得值不值」。好的分层，每一层都应该是深模块；而现实中大量分层代码的问题恰恰在于——**层数够了，深度不够**。

## 延伸

如果你的项目里有典型的 `Controller → Service → Manager → DAO` 逐级透传、或者到处是 `XxxInterface` + 单一 `XxxImpl` 的情况，那就是分层制造浅模块的重灾区，可以按上面的三个问题逐个过一遍，把「什么都不干」的层合并掉。
