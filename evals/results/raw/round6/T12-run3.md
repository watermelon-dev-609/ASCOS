# 深模块是什么意思？和普通的分层有什么区别？

## 一句话

**深模块**是 John Ousterhout（《A Philosophy of Software Design》）提出的一个**度量模块"划得值不值"的成本收益判据**：接口要窄，实现要厚。

**分层**是一种**组织依赖关系的手段**，回答的是"谁可以依赖谁"。

两者不是同一维度的东西：分层是**结构/拓扑约束**，深模块是**质量/性价比判据**。你可以分层分得很好看，但每一层都很浅——那就是一堆负债。

---

## 一、深模块的定义

> **模块的价值 = 它替调用方藏起来的复杂度；模块的代价 = 它的接口面积。**

用一个矩形表示模块：

- **宽度 = 接口**（方法数、参数个数、异常、配置项、需要了解的调用顺序/状态机、隐式约定）
- **高度 = 实现**（内部代码量、它替你做的决策、它吸收掉的问题）

**深模块** = 窄而深：接口只有几个入口，背后却藏了巨大的实现复杂度。
**浅模块** = 宽而浅：接口一大堆，内部几乎什么都不做（典型是一行 `return dao.find(id);`）。

### 经典例子

| 模块 | 接口宽度 | 实现深度 | 结论 |
|---|---|---|---|
| Unix 文件 I/O：`open / read / write / seek / close` | 5 个调用 | 几十万行：缓冲、权限、设备驱动、文件系统、页缓存 | 极深，教科书级 |
| Go / Java 的垃圾回收器 | **零接口**（你不调用它任何东西） | 数万行 | 深到极致——"它只是消失了" |
| SQL | 一套声明式语法 | 查询优化、事务、索引、并发控制 | 很深 |
| `private String name; getName()/setName()` | 两个方法 | 零 | 极浅 |
| `UserService → UserManager → UserDao` 每层都只转发 | 三层接口 | 一层代码 | 浅层堆叠 |

Ousterhout 举的反面例子是 Java 的 I/O：你想读一个文本文件，得写
`new BufferedReader(new InputStreamReader(new FileInputStream(path), "UTF-8"))`——
每一层都要求调用方做一次决策（要不要缓冲？什么编码？），**复杂度没有下沉，反而上升到了调用方**。这就是典型的浅模块串联。对比 Python 的 `open(path)` 自己带缓冲和默认编码，或者 Go 的 `os.ReadFile`。

## 二、分层的定义与它的真实成本

分层（Layer / N-Tier）是把系统按**抽象级别**自上而下切开，并规定依赖方向（通常只允许上层依赖下层）：

```
Presentation  →  Application  →  Domain  →  Infrastructure
```

它的收益是明确的：依赖可预测、可替换底层实现、便于分工和定位代码。

但**分层不是免费的**。每一层都要付"接口税"：

1. **接口税**：每层都要定义自己的 DTO、异常、入参出参，都要被学习、被文档化。
2. **透传变量**（pass-through variable）：一个 `userId` 或 `tenantId` 从第 1 层一路传到第 7 层，每层都要加参数、加字段、加转换——它不属于任何一层的抽象，只因为"分层"而存在。
3. **透传方法**（pass-through method）：`A.f() { return B.f(); }`，唯一作用是把 A 的存在感刷出来。

**所以：分层创造的是"位置"，不创造"价值"。** 价值只来自每层真正吸收掉的复杂度。

## 三、核心区别（重点）

| 维度 | 深模块 | 分层 |
|---|---|---|
| 回答的问题 | 这一块划得**值不值**？ | 代码应该**放在哪**、谁能依赖谁？ |
| 性质 | 质量度量 / 成本收益判据 | 结构约束 / 拓扑规则 |
| 关注点 | 接口宽度 vs 实现复杂度 | 依赖方向与抽象层级 |
| 失败形态 | 浅模块：接口宽、实现薄 | 无意义分层：相邻两层抽象相同 |
| 可叠加？ | 可以 —— 正解是"**层要少，每层要深**" | — |

关键洞察是：**它们是正交的，而且必须配合使用。**

- 只讲分层不讲深度 → 得到"千层饼"：7 层架构，每层 3 行转发代码，改一个字段要动 7 个文件。
- 只讲深度不讲分层 → 容易滑向"上帝模块"：一个包吞掉一切，依赖方向失控。

正确的组合是 Ousterhout 那句判据的延伸：

> **相邻两层如果抽象相同，分层就是错的。**

这是最有实操价值的一条。如果你说不清"Application 层"和"Domain 层"在**抽象**上有什么本质不同（而不只是"一个叫 Service 一个叫 Entity"），那这两层就该合并——合并之后它往往自动变成一个深模块。

## 四、怎么判断一个模块是深是浅（可操作清单）

对任意模块，问 6 个问题：

1. **调用方要记住几件事才能用对？** （方法数 + 参数 + 配置项 + 调用顺序 + 状态）
2. **调用方要理解几个它其实不关心的概念才能用？** （这就是 leaky abstraction，越多越浅）
3. **如果删掉它，调用方要多写多少代码？** （这是它真正的价值，越多越深）
4. **它替调用方做了多少个决策？** （缓冲？重试？编码？分页？事务边界？——决策越多越深）
5. **有没有"你必须先调用 X 再调用 Y"这种时序约定？** （有就是复杂度泄漏到接口上，变浅）
6. **改一个需求，要动几个模块？** （散弹式修改通常意味着层切错了，被切碎的其实是同一个深模块）

经验法则：**接口的"概念数"应当远远少于实现的"概念数"。** 一个把 30 个配置项摊给调用方的工具类，和一个需要 3 个参数却处理了 3000 行逻辑的引擎，显然后者更深。

## 五、把浅模块改深的具体手法

1. **合并下沉（Collapse）**：把 A→B→C 三层的转发链合成一个模块，接口只暴露最外层那一个。
2. **给默认值（"它只是消失了"）**：不要问调用方"要不要缓冲 / 用什么编码 / 要不要重试"，直接替他选好合理默认。每消除一个必填参数，模块就深一分。
3. **自己推断，别让调用方声明**：从上下文、注解、约定里拿信息，而不是在接口上加参数。
4. **下沉复杂度**：把"必须按顺序调 X、Y、Z"包成一个 `doThing()`；把"要自己关资源"变成 try-with-resources 或自动释放。
5. **配置外移**：把大量构造参数移到一个配置对象/构建器里，让**常用路径**的接口只有一个参数。接口宽度按"常用路径"算，不按"全部能力"算。
6. **拆成"小接口 + 大默认"**：一个窄的核心接口 + 一个可选的扩展接口，而不是一个巨接口。

## 六、边界与常见误解（重要，别走极端）

- **"深"不等于"大"。** 深指的是**接口窄**，实现大是结果不是目标。刻意堆代码不会让模块变深，只会让它变胖。
- **深模块不是上帝模块的通行证。** 如果模块的接口虽然少，但**概念上混杂**（既管用户又管计费又管邮件），那它违反的是"单一职责"，依然要拆——只是拆分的依据应是"对调用方呈现的抽象"，而不是"代码行数超过 200 就该拆"。
- **不要为了深而牺牲可测性与演进性。** 一个把数据库、网络、业务逻辑全吞进去的"深模块"，接口是窄了，但也不可测了。此时正确做法不是变浅，而是**在内部再分层**——对外深，对内清晰。
- **分层在某些场景是刚需**，与深不深无关：需要替换底层（换数据库、换云厂商）、需要边界隔离（防腐层）、需要对外提供稳定 API。这些层的价值来自"可替换性"，不来自"它做了多少事"，此时不该用深度去苛责它。
- **微服务语境下要额外小心**：服务间的网络调用是**最贵的接口**。一个只做 CRUD 转发的微服务，是"浅模块"的最贵形态——你付了序列化、网络、超时、重试、部署的全部成本，换来零抽象收益。

---

## 七、一句话总结 / 口诀

- **深模块**：接口要窄，实现要厚，复杂度要往下沉，默认值要替调用方想好。
- **分层**：层要少，相邻层的抽象必须**不一样**，透传是病，得治。
- 两者关系：**用分层定方向，用深度定粒度。** 分层告诉你"依赖往哪走"，深模块告诉你"这一层到底配不配单独存在"。

> 判断标准可以压缩成一个问题：**"我加这一层/这个模块，是让调用方变简单了，还是只是让我自己的目录结构更好看了？"**
