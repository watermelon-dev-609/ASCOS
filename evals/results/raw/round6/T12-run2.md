# 深模块（Deep Module）是什么意思？和普通分层有什么区别？

## 一句话结论

**深模块是 John Ousterhout 在《A Philosophy of Software Design》里提出的“模块性价比”标准：接口窄而简单、实现厚而强大 —— 用很少的“说”换来很多的“做”。**
而**分层（Layering）是系统级的纵向切分方式**，解决的是“谁依赖谁、职责归谁”。

两者不是同一个维度的东西，**正交**：分层可以产生深模块，也可以产生一堆浅模块。

---

## 一、深模块到底是什么

### 1. 模块 = 接口 + 实现

Ousterhout 把任何可复用的代码单元（类、包、服务、函数、API）都画成一个矩形：

```
      接口宽度
     ┌──────────┐  ← 接口：调用方必须知道的东西
     │   接口   │
     ├──────────┤
     │          │
     │   实现   │  ← 实现：模块内部真正干的事
     │          │
     └──────────┘
        深度 = 实现提供的功能量
```

- **接口的成本**：方法数量、参数个数与复杂度、调用顺序约定、需要理解的前置知识、异常种类、副作用、配置项。
- **实现的收益**：这个模块替调用方屏蔽掉的复杂度、替调用方完成的工作量。

### 2. 深模块 vs 浅模块

| | 接口 | 实现 | 观感 |
|---|---|---|---|
| **深模块** | 窄、简单 | 复杂、功能强 | “你只管说一句，剩下的我全包了” |
| **浅模块** | 宽、复杂 | 薄、几乎没干什么 | “你得先学会一堆规矩，然后它转发了一下” |

```
深模块                     浅模块
┌────────┐              ┌────────────────────┐
│ 简洁API │              │      复杂的接口      │
├────────┤              ├────────────────────┤
│        │              │  几乎没干什么的实现   │
│  强大的 │              └────────────────────┘
│  实现   │
│        │
└────────┘
```

### 3. 典型深模块例子

- **Unix 文件 I/O**：`open / read / write / close / lseek` 五个调用，背后是几千行的缓冲、权限、设备驱动、文件系统代码。接口宽度≈5，深度极大。
- **垃圾回收器（Java / Go）**：接口基本是“无”——你甚至不用调用它。它替你管理了整块最复杂的内存问题。深度趋于无穷。
- **SQL**：一句声明式的 `SELECT ... WHERE ...` 换来查询优化器、索引选择、事务、并发控制。
- **HTTP 客户端库**：`client.get(url)` 换来连接复用、TLS、重试、超时、代理。
- **`HashMap`**：`put` / `get` 换来哈希、扩容、红黑树退化处理。

### 4. 典型浅模块（反面教材）

- **纯透传的 Service 层**：`UserService.getUser(id) { return userDao.getUser(id); }` —— 接口一整套，实现一行。
- **一个个只有一两个方法的小类**：`EmailValidator`、`PhoneValidator`、`UsernameValidator`……每个都要你在别处知道它的存在和调用时机。
- **过度拆分的微服务**：服务间靠网络调用互相转发，每个服务自己没干多少事，但接口（协议、超时、重试、序列化、版本）极度复杂。
- **配置型接口**：要求调用方先填 15 个字段才能用一次，其中 12 个有默认值却偏要你显式传。
- **`getX() { return x; }` 式的“封装”**：没有任何信息隐藏，只是多了一层跳转。

> Ousterhout 的名字叫 **“classitis”（类炎）**：以为“小类 = 好设计”，结果把复杂度从实现转移到了接口和调用方身上。**复杂度不会消失，只会转移。**

## 二、那它和普通分层有什么区别

### 1. 关注点不同（核心区别）

| 维度 | 深/浅模块 | 分层架构 |
|---|---|---|
| 回答的问题 | “这个模块值不值？” | “系统怎么切、依赖往哪走？” |
| 分析对象 | 单个模块（类/包/服务/函数） | 整个系统的结构 |
| 度量方式 | 接口成本 vs 实现收益（性价比） | 抽象层级与依赖方向（有序性） |
| 典型形式 | 深/浅、“性价比” | Controller / Service / DAO、OSI 七层、领域层/应用层/基础设施层 |
| 失败模式 | 接口膨胀、透传方法、类炎 | 层间循环依赖、职责错位、层次过薄或过厚 |

**分层是“怎么切”，深浅是“切得好不好”。**

### 2. 两者正交：分了层，也可能是浅的

一个经典的“分层但很浅”的例子：

```
Controller.getUser(id)
   └─> UserService.getUser(id)
          └─> UserDao.getUser(id)
                 └─> JDBC: SELECT * FROM user WHERE id = ?
```

四层，其中两层是纯转发。这就是 **pass-through method**：
- 改一个字段要改 4 个文件（甚至 4 个服务、4 个 DTO）；
- 每层都要求你理解一遍同名的 `UserVO / UserDTO / UserPO` 转换；
- 出问题时你要在 4 层里打断点；
- 但每层自己几乎没解决任何实质问题。

**分层完全正确，但每个模块都很浅 → 整体复杂度反而上升。**

反过来，**分层也可以很深**：比如把“权限 + 缓存 + 审计 + 分页”全部收进一个 `Repository` 层，上层只写 `repo.findActiveUsers(page)`，中间的缓存一致性、软删除过滤、数据权限全部在这一层内部消化 —— 层没变少，但每层变深了。

### 3. 分层的价值 vs 深模块的价值

- **分层的收益**：依赖方向清晰、可替换（换数据库只动 DAO）、职责可定位、便于团队按层分工、隔离技术细节。
- **深模块的收益**：**认知负担**低。调用方需要装进脑子里的东西越少越好。

真正好的架构是：**分层提供秩序，深模块提供效率。** 只做前者不做后者，就会得到“整齐的屎山”。

## 三、怎么判断自己的模块深还是浅

问自己几个问题（接口侧的“成本清单”）：

1. 调用方要调用几个方法、传几个参数才能完成一件事？
2. 有没有**调用顺序**要求（必须先 init 再 setX 再 execute）？
3. 有没有**透传变量**（一个参数从最上层一路传到最下层，中间没人用）？
4. 有多少异常/错误码需要调用方分别处理？
5. 有没有“约定俗成但没写在签名里”的前置条件？
6. 把这个模块的内部实现全删掉，换成一个最蠢的实现，调用方代码要改多少？——**改得越少，模块越浅。**

第 6 条是最锋利的一刀：如果删掉实现、只留转发，系统照样能跑，那这层就是浅的。

## 四、实践建议（怎么把分层做得更深）

1. **拆分的判据是“信息隐藏”，不是“代码行数”。** 300 行但内聚地解决一类问题的类，比 10 个 30 行互相调用的类更好。
2. **层必须有“抽象增值”。** 每加一层，问：这一层替上层屏蔽掉了什么？答不上来就不要这层。
3. **消灭透传方法和透传变量。** 要么让中间层真的做点事（校验、缓存、鉴权、编排），要么允许上层直接调用下层。
4. **接口尽量“声明式 + 默认值”**：让调用方说“要什么”，而不是“怎么做”。配置项收敛成一个 options 对象，而不是 15 个位置参数。
5. **允许合理的跨层调用。** 严格的“必须走 Service”如果只带来转发，那是在用规则制造浅模块。
6. **微服务拆分别过细。** 每拆出一个服务，就多了一个网络边界（超时、重试、幂等、版本、可观测性）——这是极其昂贵的接口。
7. **优先做“信息隐藏”的抽象，而不是“分层”的抽象。** 一个隐藏了“数据存在哪、怎么缓存、怎么鉴权”的 Repository，远比 Controller/Service/DAO 三层转发有价值。

---

## 五、速记版

> - **深模块 = 窄接口 + 强实现 = 高性价比 = 认知负担低。**
> - **分层 = 按抽象级别切分、规定依赖方向。**
> - **分层不等于好设计：层次分得再清楚，如果每层都只是转发，整体就是一堆浅模块。**
> - **复杂度不会消失，只会转移 —— 要么留在实现里（深，好），要么摊到接口和调用方身上（浅，坏）。**
