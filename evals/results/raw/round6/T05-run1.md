# 需求：接一下微信支付

## 一、任务判定与路由

- **意图识别**：新增支付能力 = 新功能 + 对外接口 + 涉及资金流转。
- **任务级别**：**至少中**。依据路由表「含任一：鉴权 / 支付 / 对外接口 → 至少中」，因此**强制安全审查**；若后续上线则**强制发布检查**。
- **需求完整度**：一句话需求，信息严重不足（支付产品形态、商户模式、业务范围、技术栈均未说明）。
- **调用链**：`requirements` → `architecture`（读 `references/security.md`）→ `implementation` → `verification`

## 二、requirements 阶段结论：**失败（阻断）** → 返回待确认项清单

按 Skill 契约，`requirements` 的失败状态是「存在阻断性业务决策缺失 → 返回待确认项清单，**不得静默降级**」。
微信支付的产品形态分支极多，选错会导向完全不同的实现（商户号体系、证书体系、下单 API、前端链路、回调字段全都不同），属于「两条实现路径导向完全不同产品形态」，必须停下来问，**不进入编码**。

### 待确认项（阻断，需你拍板）

1. **支付产品形态**（决定下单 API 与前端链路，可多选）
   - JSAPI（公众号 / 小程序内支付，需 openid）
   - Native（PC 端扫码支付）
   - H5（非微信内浏览器）
   - App（移动端 SDK）
2. **商户模式**：直连商户 / 服务商（服务商模式下需 `sub_mchid` / `sub_appid`，下单参数与回调字段均不同）
3. **业务范围**：仅「支付」，还是包含 退款、订单查询、关闭订单、对账单下载、分账？（建议首期至少含：支付 + 回调 + 查询 + 退款）
4. **技术栈与订单落点**：后端语言 / 框架、数据库与 ORM、是否已有订单表、幂等机制与订单状态机？（我会先感知代码库再设计，不另起炉灶）
5. **回调通知地址 `notify_url`**：公网可达域名 + 路径，HTTPS 是否已就绪
6. **联调环境**：是否有沙箱 / 测试商户号；真实商户号何时可用

### 凭证获取方式（重要：不要在本对话中发给我）

- 需要的配置项：`WECHATPAY_MCHID`、`WECHATPAY_APPID`、`WECHATPAY_API_V3_KEY`（32 位）、`WECHATPAY_PRIVATE_KEY_PATH`、`WECHATPAY_CERT_SERIAL_NO`，平台证书由服务端自动下载并按序列号缓存。
- 一律走**环境变量 / 密钥管理**注入；私钥文件置于项目外或 secrets 目录并加 `.gitignore`；**我不接收明文口令与密钥**，日志中对商户号、订单号、签名做脱敏。

### 我已自行补全的假设（无需你确认，若否决请说明）

- 采用微信支付 **API v3**（v2 不建议新接入）。
- 服务端统一下单，前端只消费 `prepay_id` / `code_url` / `mweb_url`，**不参与签名**。
- 回调必须：验签（`Wechatpay-Signature` 等头部）→ 解密 `resource`（AES-256-GCM）→ 幂等去重 → 才推进订单状态；**回调成功才算支付成功**，主动查询仅作兜底。
- 金额全程使用**整数分**，禁止浮点。
- 商户订单号贯穿全链路，日志可追溯，便于对账与排障。

## 三、确认后的执行计划

1. 读 `references/repository-awareness.md` 并消费 `CONTEXT.md`，先摸清现有订单 / 用户 / 配置体系（先感知代码库，再动手）。
2. `architecture`：设计模块与接口（下单 / 回调 / 查询 / 退款）、订单状态机与幂等键、变更影响清单、ADR；同时读 `references/security.md` 执行**强制安全审查**。
3. **技术事实新鲜度**：动手前查微信支付官方文档，确认 APIv3 当前的签名、回调、平台证书规范（`research-freshness`），不凭记忆编写涉及资金与加密的逻辑。
4. `implementation`：TDD 红绿循环，先补回调验签 / 解密 / 幂等的测试，再写实现；下单与状态推进走可测试的 seam。
5. `verification`：Build / Test / Lint / Type Check 的真实证据 + DoD 逐项判定；若上线再补 `release` + `observability` 发布检查。
