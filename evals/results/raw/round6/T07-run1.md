## 1. requirements — 需求补全（事实 / 假设 / 建议 分开标注）

### 事实（来自用户原话）
- 需求对象：订单列表。
- 需要新增：分页、关键字搜索。

### 假设（我自行补全，**如与实际不符请直接纠正**）
1. 分页形态采用**页码分页**（page + pageSize），前端需要展示总数与跳页；若数据量将达十万级以上，建议改为游标分页（见 §4）。
2. 关键字搜索对象为**订单号 + 客户名/手机号**这类业务可见字段，采用**大小写不敏感的包含匹配（LIKE %kw%）**。
3. 搜索与分页**可组合**：先按关键字过滤，再分页，排序保持与现状一致且**必须含唯一 tie-breaker**。
4. 列表受**数据权限约束**：用户只能看到自己/本租户的订单；搜索不能穿透该边界。
5. 默认 `pageSize=20`，上限 `pageSize=100`。
6. 关键字空串 / 全空白 → 视为不过滤；长度 < 2 建议前端不发请求（避免全表扫）。

### 建议（非必须，但强烈建议纳入）
- 搜索输入框 **300ms 防抖**，输入变化**自动重置到第 1 页**。
- 分页与关键字**同步到 URL query**（可分享、可刷新、可后退）。
- 明确三态 UI：加载中 / 空结果（区分「无数据」与「无匹配结果」）/ 请求失败可重试。

### 我主动补齐的边界（用户没说但会踩坑）
| 边界 | 处理方案 |
|---|---|
| SQL 注入 | 关键字**必须参数化**；`LIKE` 的 `%` `_` `\` 必须转义 |
| 深分页性能 | `LIMIT/OFFSET` 在深页会退化；建议 `pageSize` 上限 + 必要时 keyset 分页 |
| 排序不稳定 | 排序字段不唯一会导致翻页重复/漏行 → 追加 `id` 作为次级排序 |
| COUNT 成本 | 大表 `COUNT(*)` 随过滤条件变慢；可接受则用估算值或异步计数 |
| 越权 | 搜索条件与分页必须叠加在同一权限过滤作用域内，不可先查全表再过滤 |
| XSS | 关键字回显到页面（"搜索：xxx"）需转义，禁止 `innerHTML` 拼接 |
| 特殊字符 | 关键字含 emoji / 超长串（> 100 字符）需截断与拒绝 |
| 导出一致性 | 若页面有"导出全部"，需明确：导出受同一关键字与权限约束（否则数据泄露） |
| 可观测性 | 记录慢查询日志（p95 耗时、命中索引、返回行数），新接口加埋点 |

### 需确认的阻断项（**这 5 条会改变实现方式，请确认后我再动代码**）
1. **技术栈 / ORM 是什么？**（后端语言 + 框架 + ORM，前端框架）— 决定代码形态。
2. **分页形态**：页码分页（要总数/跳页）还是游标分页（只要上一页/下一页）？
3. **搜索字段与匹配规则**：搜哪些字段？包含匹配还是前缀匹配？是否要支持多关键字空格分词？
4. **默认排序字段**是什么？（决定索引设计）
5. **是否必须返回精确 `total`？** 若允许"仅显示有无下一页"，可省掉 COUNT，性能大幅提升。

## 2. 验收标准（Given / When / Then）

**分页**
1. Given 订单共 35 条、pageSize=20，When 请求 page=1，Then 返回 20 条 + total=35 + 存在第 2 页。
2. Given page=999，When 请求，Then 返回空数组 + HTTP 200，不报错。
3. Given page=0 / -1 / 非数字 / pageSize=99999，When 请求，Then 返回 400 参数校验错误（或按上限收敛），不产生全表扫描。
4. Given 两次请求 page=1 与 page=2，Then 两页结果**无重复、无遗漏**（需唯一排序键保证）。
5. Given 排序字段存在大量相同值，When 连续翻页，Then 不出现同一行在两页重复。

**搜索**
6. Given 关键字 "1001"，When 搜索，Then 仅返回订单号或客户信息包含 "1001" 的订单。
7. Given 关键字 "50%"，When 搜索，Then 按**字面量** "50%" 匹配，而非被当作通配符匹配任意字符。
8. Given 关键字 "' OR 1=1 --"，When 搜索，Then 返回空结果且不报错（参数化生效）。
9. Given 关键字 "  "（纯空格），When 搜索，Then 等价于不搜索，返回全量分页结果。
10. Given 用户 A 与用户 B 的数据同时存在，When A 搜索 B 的订单号，Then 返回空（权限边界不可被搜索穿透）。

**组合与非功能**
11. Given 关键字命中 5 条，When 翻到第 2 页（每页 20），Then 返回空且 total=5。
12. Given 输入关键字，When 关键字变化，Then 自动回到第 1 页。
13. 接口 p95 响应时间在目标数据量下满足既有 SLO（需给出基线数字再定阈值）。
14. 前端输入 300ms 内连续输入 5 个字符，只发出 1 次请求。

## 3. implementation — 实现方案（骨架，待按实际栈落地）

### 3.1 API 契约
```
GET /api/orders?page=1&pageSize=20&keyword=1001&sort=createdAt:desc

200 → {
  "items": [ { "id": "...", "orderNo": "...", ... } ],
  "total": 35,          // 若确认项 5 选"不需要总数"则改为 hasNext
  "page": 1,
  "pageSize": 20
}
400 → { "error": "INVALID_PARAM", "message": "..." }
```
- 参数校验：`page` 正整数、`pageSize` ∈ [1,100]、`keyword` trim 后长度 ≤ 100。
- **向后兼容**：`page`/`pageSize` 给默认值，旧调用方不传仍能工作。

### 3.2 数据层（SQL 示意）
```sql
-- 参数化 + 转义，禁止字符串拼接
SELECT id, order_no, customer_name, status, created_at
FROM orders
WHERE tenant_id = :tenantId                                  -- 权限过滤必须在同一作用域
  AND (:keyword IS NULL OR
       order_no LIKE :kw ESCAPE '\' OR customer_name LIKE :kw ESCAPE '\')
ORDER BY created_at DESC, id DESC                            -- id 为唯一 tie-breaker
LIMIT :pageSize OFFSET :offset;
```
- 关键字预处理：`kw = '%' + escapeLike(keyword.trim()) + '%'`，`escapeLike` 依次处理 `\` `%` `_`。
- 索引：按确认项 4 的排序字段建复合索引，形态参考 `(tenant_id, created_at DESC, id DESC)`；关键字走前缀匹配时才能用上索引，`LIKE '%kw%'` 天然无法用 B-tree 索引 → 若数据量大，需引入全文索引/搜索引擎，这是**架构分叉点**，先确认数据量。

### 3.3 前端
- 输入防抖 300ms → 触发查询；关键字变化 `resetPage()`。
- 分页/关键字写入 URL query（替换而非叠加 history，避免污染后退栈）。
- 三态：loading骨架屏 / 空态（"没有订单" vs "没有匹配的订单，试试其他关键字"）/ 错误态带重试。
- 关键字回显走文本节点，不用 `innerHTML`。

### 3.4 测试
- 后端：参数校验边界、转义（`%`/`_`/`\`）、注入串、越权隔离、翻页无重复无遗漏、深页空结果。
- 前端：防抖只发一次请求、关键字变更重置页码、空态文案。
- 性能：在**接近生产的量级**下跑一次，取基线数字，不要凭感觉。
