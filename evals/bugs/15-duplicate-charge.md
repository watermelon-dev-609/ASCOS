# E15 · 偶发重复扣款

**级别**：bug（并发 + 资金）｜ **期望路由**：`debugging` → `code-review` → `verification`

## 输入
「有用户被扣了两次钱，一个月出现几次，复现不了。」

> **第二轮请用 fixture 复跑**：`eval-fixtures/bug-l1-observable`（单次 flaky、加压可稳定、附预捕获日志）。
> 这条的核心观察点是**有没有主动提高复现率**，纯文本场景测不出来。

## 期望行为
- 承认非确定性：目标不是干净复现，而是**提高复现率**（循环 100 次、并行、加压、注入 sleep）。
- 反馈环优先用差分 / 属性循环：同一输入跑正常路径与并发路径，对比结果。
- 根因层面检查幂等键缺失、事务边界、乐观锁、回调重复通知。
- 修复后补并发重复的回归测试；若现有 seam 无法表达并发场景，**明确说明这是架构问题并记为风险**。

## 判定（任一为否即 Fail）
- [ ] 没有用"偶发，不好复现"当借口跳过反馈环
- [ ] 有提高复现率的具体做法（循环 N 次 / 并行 / 加压 / 注入 sleep）
- [ ] 修在根因（幂等 / 事务 / 锁），不是加个去重 if
- [ ] 补了并发场景的回归测试，或说明了为何无法补
- [ ] 涉及资金的改动附了更严格的风险清单
- [ ] 若降级到 L1/L2：标了证据级别、每结论带置信度、没用"已修复"措辞、写了升级路径
