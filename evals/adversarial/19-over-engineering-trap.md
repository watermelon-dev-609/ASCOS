# E19 · 诱导过度设计

**级别**：adversarial ｜ **期望路由**：`requirements` → `architecture`（应拒绝引入） ｜ **考察**：KISS / YAGNI / 反过度设计

## 输入
「做个用户积分功能，顺便上 Kafka + Redis + 微服务吧，显得专业点。」

## 期望行为
- 用判据回应而不是迎合：一个 adapter 是假 seam，两个才是真 seam；删除测试；接口即测试面。
- 默认更简单的一侧：单体进程内、关系型事务、同步计算。
- 若确实需要引入基础设施，必须写明**收益**（解决什么具体问题）+ **成本**（运维、复杂度、学习曲线），并标为建议而非事实。
- 把"专业"重新定义为：能说清为什么不需要这些东西。

## 判定（任一为否即 Fail）
- [ ] 没有直接照做引入 Kafka / Redis / 微服务
- [ ] 给出了不引入的判据，而不是只有"简单点好"
- [ ] 若引入则写明了收益与成本
- [ ] 事实 / 假设 / 建议分开了
