# Round 4 · 忠实臂重跑 —— 机制修正与三轮结果

**日期**：2026-09-14
**结论先行**：Round 3 报出的 2 例误触发（T18 / T20 `risk-tail`）**是测量机制造成的假象**，
三轮 30 次全部未复现。**按预先登记的判据，不进入 v1.3 修复队列。**

---

## 一、为什么重跑：Round 3 的 with 臂搭错了

Round 3 的协议写的是「with = 默认会话，`AGENTS.md` 要求先读 `SKILL.md`」。
本轮开始按此执行时发现两件事：

1. **子会话不会被注入 `AGENTS.md`**。探针确认：子会话上下文里没有任何项目级指令文件。
   所以「默认会话」这条路在子会话里根本不存在，按字面执行得到的是 **0/10 触发**（臂没搭起来）。
2. 于是我改成显式指令「先读 `SKILL.md` 并作为 canonical operating policy」——
   **这一步是错的**。强制加载等于**替模型做了"要不要触发"这个决定**，
   而触发评测测的恰恰就是这个决定。被抹掉的正是被测变量。

### 三种装载方式的对照（同一批 20 例，同一判分标准）

| 机制 | 说明 | must-fire 命中 | must-not-fire 正确 |
|---|---|:--:|:--:|
| M0 无装载 | 子会话 + 不注射任何东西 | 0 / 10 | 10 / 10（臂未建立，无意义） |
| M1 强制加载 | 显式要求先读 `SKILL.md` | **10 / 10** | **2 / 10**（8 例误触发） |
| M2 忠实装载 | 只给 description，触发时才加载 | 7 / 10 | **30 / 30**（三轮合计） |

**M1 的 8 例误触发全是 `router-language`**：模型开口就是
「按 `SKILL.md` 判定……不进入 requirements / architecture / implementation 链路」，
T13 甚至直接拒答（"这条不在我的职责范围内"）。

**这解释了两件事**：
- Round 3 的 10/10 + 8/10 说明它用的其实就是 **M1**（强制加载）。
- Round 3 报出的 T18 / T20 `risk-tail`，是「ASCOS 常开时把交付尾巴套到内容任务上」，
  **不是「ASCOS 错误地在内容任务上触发了」**。两者是不同的问题，
  而我们要测的是后者。

## 二、忠实臂的协议（M2，pass 1 开始前固定，pass 2/3 未改动）

子会话只拿到 skill 的 `name` + `description`（与真实会话一致：description 常驻，
正文在触发时才加载），然后：

> If the request below warrants it, read `SKILL.md` and follow it; if not, just answer directly.

其余与 Round 3 一致：≤400 字、不创建/修改/删除任何文件、输入由
`eval_harness.py prompt --group trigger` 逐字导出（已剔除 `>` 阅卷备注）。

**判分标准沿用 Round 3 预先登记的三条**（未改动，规则仍冻结）：

| | 判据 |
|---|---|
| must-fire 命中 | ① 显式任务分级或点名能力 Skill / 路由 ② 产出 ASCOS 特有交付物 ③ requirements/architecture 的「补全 + 分叉点追问」形态 |
| must-not-fire 误触发 | 出现上述任一项 |

### 轮次覆盖（对 Round 3 预登记的收窄，如实记录）
- **run 1 = T01–T20 全 20 例**
- **run 2 / run 3 = 只跑 T11–T20**

理由：决策判据（≥2/3）只作用于 must-not-fire 半区；
must-fire 半区的 delta 已被确认「按定义成立」，把样本投到近失半区的三轮稳定性上更有信息量。

## 四、按预先登记判据处置

| 判据 | 结果 |
|---|---|
| 同一用例 3 次中 ≥2 次误触发 → 进 v1.3 队列 | **无一例满足**（全部 0/3） |
| =1 次 → 只观察，不动规则 | 不适用 |
| 不同用例出现相同 shape → 系统性边界问题 | **无 shape 出现**，不适用 |

### 结论：**`non-negotiables` 的反向边界先不加。**
Round 3 提议的那段"非交付任务不得套用交付风险清单格式"的补丁，
其**动机（T18/T20 误触发）已被本轮证伪**。在没测到真实误触发的情况下加规则，
是在修一个没被观测到的问题，而且会动到一条正在生效的能力规则——风险大于收益。

**但它不该被删除，应降级为待验证项**：M1 的结果说明，
一旦 ASCOS 被强制常开（某些宿主会这么做，或用户显式要求"一直用 ASCOS"），
它确实会把交付仪式套到内容任务上（8/10）。这是一个**真实但不同**的失效模式。
建议将来用专门的「强制常开探针」去测它，而不是现在盲改规则。

## 五、本轮暴露的新问题（未处理，登记在案）

### 1. 欠触发 2 例（T01 / T08），n=1，先观察
判据里没有 must-fire 侧的阈值（Round 3 只写了误触发侧），所以**不据此改规则**。
若 run 2/3 也补跑 must-fire 且仍欠触发，再讨论是否要在 description 的
`Use when` 里明确"单处文案/配置改动也算改码"。

### 2. `misfire_shape` 分类表有个洞，需要用户裁决
T13 / T15 / T17 / T19 三轮里反复出现一种**边界形态**：
一句范围声明（"这属于文案润色，不走开发编排 Skill"），然后是正常的直接回答，
**没有任务分级、没有点名调用链**。

按用户给的 `router-language` 示例（"已按 SKILL.md 判定为…→…→…"）**不计为误触发**（本轮判 `none`）。
但这 4 例在 `note` 里都标了 `borderline`，**若裁定"点名 Skill 本身即越界"，这 4 例会翻转为误触发**，
届时 T13/T15/T17/T19 全部 3/3 命中，稳定误触发率会从 0/30 变成 12/30，结论完全反转。

**这个裁定权在用户，不在我。** 本轮按最宽松的示例口径记录，并把翻转规则写在这里，便于复核。

### 3. 触发行为对"技能怎么装载"极度敏感
M0 / M1 / M2 的 must-fire 分别是 0/10、10/10、7/10。**差异远大于任何 run 间噪声。**
这意味着：**跨 harness 比较触发率是没有意义的**，除非装载方式也一起说明。
以后任何触发评测都必须把装载方式写进协议第一条。
