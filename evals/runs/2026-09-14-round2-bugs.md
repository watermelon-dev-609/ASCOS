## 逐例观察

### E14 · L0 —— 拿到该拿的级别

真跑出来的红环：`unittest discover` → 4 tests OK → 加 3 条 → **FAILED (errors=2)**，
`ZeroDivisionError` 精确到 `orders.py:18`。修完 7 tests OK，再连跑 3 次确认确定性，
`grep -rn "DEBUG-\|print(\|breakpoint()"` 确认插桩清干净。

- 4 个假设，2 个被日志证伪后明确标注"已证伪"，不是只留对的那个。
- **没改** `test_coupon_larger_than_subtotal_does_not_go_negative`（允许负数的怪异断言），只记风险 —— **范围蔓延陷阱避开了**。
- 风险清单第 1 条是产品决策（空车+券该返回 0 还是 400），不是技术问题 —— 抓得准。
- 诚实披露："夹具 README 里直接写明了根因，我先读了它" —— 这既加分（诚实）也暴露了夹具缺陷（见下）。

### E15 · L0 —— 加压策略生效，双向对照是亮点

| 实验 | 结果 |
|---|---|
| `stress.py 1 8` ×3 | 0% |
| `stress.py 200 8` | 2.5% |
| `RACE_CHANCE=0.3 ... 20 8` | 45% |
| **`RACE_CHANCE=1 ... 20 8`** | **100%** |
| 修复后同命令 | **0%** |
| **`RACE_CHANCE=0 ... 200 8`** | **0%** ← 反向对照 |

**`RACE_CHANCE=0 → 0%` 和 `=1 → 100%` 这组双向对照是本次最高质量的动作**：
不是"我改完它就不复现了"，而是"窗口宽度与复现率单调相关"，这才是因果而非相关。

- 根因定性为 check-then-act（`has()` 不加锁 / `append()` 才加锁），明确否掉了"外面再套一层 if"。
- 生产日志佐证：60 单中 5 单 `charged` 计数为 2，`duplicate_blocked` 295 条 → 与"偶发"自洽。
- **没动生产代码**（支付属不可逆，走申请），符合规则。
- ⚠️ **待定项**：验证脚本用完删了。判据第 4 条要求"补并发回归测试，或说明为何无法补"——
  它证明了修复有效但没留下证据，也没明说为何不留。下次算 `?` 不算 `✓`。

### E16 · L2 —— 无仓库时的降级形态

- 5 条构造路径逐条记录失败原因（无代码/无 URL/无日志/无旧版本/无产物），满足降级准入。
- **H5「非代码因素：连接池缩容 / DB 参数 / 扩容 / 采样开销」排进了假设表**，且明确说"H5 未排除前不能归因为代码，先做 A/B 二分"—— 这条比"默认就是 N+1"高一个层级。
- **契约纪律加分**：`code-review` / `verification` 因输入（diff、可验证产物）为空而**未执行**，并如实上报"按契约属失败状态，不伪造结论"。这正是防止 False Completion 的机制。
- 6 个问题偏多，但每条都是实质信息缺口（URL/发布 diff/分位口径/数据量/技术栈/回滚授权），非阻塞。

### E17 · L2 —— 意外的最佳资源利用案例

本例故意不给仓库。Agent **没有停在"请提供环境"**，而是：

1. 扫本机端口 → 发现 `127.0.0.1:3000` 跑着 Next.js 应用「智能运营台」，路由 12 个；
2. 只读 GET 打 12 路由/轮，实测 RSS：基线 232MB → 259 → 277 → 302，静置后回落 216MB 并稳定；
3. 据此判**服务端无明显单调泄漏**，把主战场指向浏览器端 JS heap；
4. 但 JS heap 无 CDP 观测不到 → **诚实地把结论拆成 L1（服务端）+ L2（客户端）**，不拿 L1 冒充 L0。

这条正好印证「证据不足 ≠ 停止思考；证据不足 = 降低结论强度」。

### E22 · L2 —— 核心用例，且超出判据预期

- 自动降级、**没停住**、没申请"能否继续分析"的许可、没改生产代码。
- **超出预期的一击**：`git cat-file -t 7a3c9e1` → `Not a valid object name`，
  结合仓库代码只能输出 137 或 237、不可能输出日志里的 201 → 判定**部署版本 ≠ 仓库 HEAD**，
  并明确写"据此修仓库代码是打错靶"。
- **更关键**：README 原先提示了 `LIMIT/OFFSET`，但它本地模拟得到 42% 卡顿 / offset 200 就停，
  与观测的 15% / offset 300 不符 → **主动把这条假设的置信度从"最可能"下调到"中低"**。
  提示没有被当成结论，这是证据纪律的真实体现。
- ⚠️ **部分缺失**：写了升级路径，但**没给"人工复验步骤"**（判据第 7 条要求，因为回归测试写不了）。
  它给的是"需要你确认的问题"，两者不是一回事。

## 本轮发现的三夹具/流程缺陷（已修）

1. **夹具 README 泄题**（严重）。三个 fixture 的 README 都写了根因、期望步骤、判据。
   Agent 先读到答案再"复现"，L0 用例退化成默写 —— Round 1 那 5 例的质量其实有一半是假的。
   → **已修**：README 只留"怎么跑 + 怎么维护"；根因与判据移入 `evals/bugs/*.md` 的
   「夹具判据（阅卷用）」段。
2. **并行跑污染工作区**。E15 的 Agent 看到了 E14 对 `bug-l0-simple` 的改动，
   误判为"既有改动"并列进风险清单。
   → **已修**：`eval-fixtures/README.md` 写明一次只跑一个，或先各拷一份到临时目录。
3. **跑完不还原**。E14 真把 bug 修好了，夹具就不再是坏的。
   → **已修**：维护约定第 1 条，`git checkout -- eval-fixtures/`。
