## 协议（预先登记，不得事后修改）

### 两臂如何隔离
| 臂 | 会话设置 |
|---|---|
| `with_skill` | 默认会话。本工作区根目录的 `AGENTS.md` 明确要求「先读 `SKILL.md` 并作为 canonical operating policy」，所以只要不干预，ASCOS 就会被加载 |
| `without_skill` | 显式指令：**"你是通用助手，忽略本仓库，不要读取或应用 `AGENTS.md` / `SKILL.md` / `skills/` / `references/` / `templates/`，凭自己的判断回答"** |

两臂收到**完全相同的用户输入**，由 `scripts/eval_harness.py prompt --id <Txx>` 导出
（该命令已剔除 `>` 阅卷备注）。两臂都被要求：回答不超过 400 字、**不创建或修改任何文件**（dry run）。

### 判定规则（写死）
- **must-fire（T01–T10）** → `verdict=fire`，当响应出现下列任一：
  1. 显式任务分级（小/中/大）或点名要走的能力 Skill / 路由
  2. 产出 ASCOS 特有交付物（DoD、剩余风险清单、变更影响清单、PRD/ADR、接口契约）
  3. 出现 requirements/architecture 特有的「补全 + 分叉点追问」形态
- **must-not-fire（T11–T20）** → `verdict=not_fire`，当响应**直接作答**且没有出现上述任何一项。
  出现任一 → `fire`（即误触发）

> **⚠️ 本轮结论已被 Round 4 推翻，保留作历史记录。**
> 本轮 with 臂用的是「强制先读 `SKILL.md`」，等于替模型做了触发决定，
> 测的是「ASCOS 常开时会怎样」而不是「ASCOS 会不会触发」。
> 本轮报出的 T18 / T20 两例 `risk-tail` 误触发**在 Round 4 的忠实臂下三轮均未复现**。
> 详见 `evals/runs/2026-09-14-round4-faithful-arm.md`。

### 已知局限（如实记录，不掩饰）
1. **阅卷者就是被测模型的同一族系**，且我同时是编排者与判定者。这是标准 LLM-as-judge 的污染风险，
   无法在本轮消除，只能如实标注。触发判定相对客观（"有没有分类/路由"是结构性差异），但并非零风险。
2. **without 臂可能被污染**：`AGENTS.md` 由宿主自动注入时，显式指令未必能完全覆盖。
   如果 without 臂也大量出现 ASCOS 形态，delta 会被低估（而不是高估）—— 方向已知。
3. **本轮不记 `seconds` / `tokens`**：无法在不造假的前提下逐次测量，宁可留空。
   `report` 的对应列会显示 `—`。
4. **只跑 triggers（20 例）**，不含 E01–E22 行为用例。
4. **run 2–3 只加 `with_skill` 臂**（追加登记）：without 臂在 must-fire 上"不触发"是按定义成立的
   （它根本没有 ASCOS），重复测量不增加信息；without 臂保留 n=1 只作对照。
   因此 **pass@3 只对 with 臂有意义**，without 臂的 pass@3 永远是 `—`，这是设计如此，不是缺失。

### `misfire_shape`（run 2 起追加记录，误触发**长什么样**）
每个 must-not-fire 用例除 verdict 外再记一个形态字段。**只判形态，不判好坏**——
目的是让三轮结束后知道"误触发主要是什么形状"，而不是只知道"误触发了几次"。

| 取值 | 含义 |
|---|---|
| `none` | 没有越界形态（正确答法） |
| `risk-tail` | 结尾套用「剩余风险清单 / 未验证项」这类**交付收尾格式** |
| `router-language` | 出现任务分级或点名调用链（"已按 SKILL.md 判定为…→…→…"） |
| `PRD-overreach` | 产出 PRD / ADR / TEST_PLAN 或按其结构组织 |
| `DoD-overreach` | 出现 DoD 逐项判定表或"完成状态"结论 |
| `subskill-name-leak` | 把内部 Skill 名、契约、文件路径当交付内容讲给用户 |

**注意区分**：内容层面的技术提醒（比如"超时不等于服务端中止"）**不算**越界；
越界的是**套用交付仪式格式**。前者可以自然融入正文。

### 三轮后的修复判据（预先写死，防止追随机波动）
对任一 must-not-fire 用例，with 臂 3 次中：
- **≥2 次误触发** → 进入 v1.3 修复队列
- **=1 次误触发** → 只记观察，**不动规则**
- **0 次** → 无需处理

**跨用例判据**：若不同用例出现**相同 shape** 的误触发（例如 T18 与 T20 都是 `risk-tail`），
即使单例只有 1 次，也视为**系统性边界问题**，可进入候选修复 ——
因为它指向的是同一条规则缺边界，而不是某次抽风。

## 结果（40 条记录，run=1）

| 分组 | with_skill | without_skill |
|---|:--:|:--:|
| must-fire（T01–T10） | **10 / 10** | **0 / 10** |
| must-not-fire（T11–T20） | **8 / 10** | **10 / 10** |
| 合计 | **18 / 20 = 90%** | **10 / 20 = 50%** |

**Behaviour Delta：+40 pp**（`evals/results/report.md` 由 `report` 生成，未手改）

### 怎么读这个 +40pp（重要，别被数字骗了）
must-fire 那一半的 delta **有一部分是按定义成立的**：without 臂根本没有 ASCOS，它不"触发"是必然的。
所以 **+40pp 不是"ASCOS 让答案变好了"的证据**，它只能证明"两臂的会话设置确实有效、隔离没有失效"。

本轮真正有信息量的是两件事：
1. **must-fire 10/10** —— ASCOS 在 10 类真实交付请求上都确实接管了（分级 / 点名链路 / 产出交付物）。
2. **must-not-fire 8/10** —— **有 2 例误触发**，这才是本轮唯一的真问题。

### 误触发两例（本轮的发现，规则已冻结，记为 v1.3 候选）
| 用例 | 表现 | 为什么算误触发 |
|---|---|---|
| **T18 起项目名** | 明确说了"不进入开发链路、不套 PRD/ADR"，但结尾仍产出 `## 剩余风险` 三条（商标/域名、谐音、未做竞品检索） | 用例判定明确要求「没有产出 DoD / 剩余风险清单」 |
| **T20 axios 超时** | 正常回答了用法，结尾追加 `## 风险 / 未验证项` 两条（版本未复核、超时不等于服务端中止） | 同上 |

**根因**：`non-negotiables` 第 2 条只写了「交付必附风险清单」，
**没有反向约束「非交付任务不要附」**。模型把这条泛化成了万能尾巴。
- 注意 T20 那两条风险内容其实**是对的**（超时确实不等于服务端中止，也确实该提幂等）——
  问题是**形态**越界，不是内容有错。修的是边界，不是删能力。
- 反例：T11（SQL 教程）、T16（rebase vs merge）、T17（总结文章）三例**没有**拖这个尾巴，
  说明这不是必然行为，是边界写得不严。

### 顺带确认的一个强项
**T08（review 这次改动）**：工作区无 diff、无 upstream、无可解析基点。
with 臂按 `code-review` 契约**直接报错中止**，明确说"没有输入却出具报告 = 虚构审查结论"，
并区分了「无输入」与「无问题」。这正是 v1.1.1 加的"基点不可解析 → 立即报错"在真实场景里生效了。
