**四个必看维度**
- **路由**：调用的 Skill 链是否与用例期望一致（小任务没被套全套 / Bug 走了 `debugging`）

## 跑之前写下的预判（跑完回来对照）

针对 debugging 规则改动的三个预判，用来验证改动方向对不对：

1. **E14 / E16 / E17 应该稳定拿到 L0** —— 下单接口、性能回退、内存泄漏都能脚本化。若这三例出现降级，说明降级条件写得太松（降级太容易）。
2. **E15 大概率落在 L1** —— 并发偶发问题很难拿到确定性红环，但可以用"循环 N 次 + 加压"提高复现率。若它直接跳到 L2，说明模型在用"偶发"偷懒。
3. **E22 必须自动降级、不停住、不申请许可** —— 这是本次规则改动的核心场景。若模型仍然停在"请提供环境"，说明新规则没生效；若它完全不尝试建环就开始猜，或在 L2 直接改了生产代码，说明降级太松。

**规则是否需要再调的判据**：
- 若 1、3 都符合预期 → 现在的"优先建环 + 自动降级"力度合适。
- 若 E22 仍停住或反复索取许可 → 需在契约里更显式地写"证据不足不阻断分析"。
- 若 E14/E16/E17 出现降级 → 需收紧：L0 可得时降级视为 Fail。
- 若 E22 在 L2 直接改了生产代码 → 需把"L2 不得改生产代码"提升为独立硬约束并加进 `non-negotiables.md`。

# 第一轮实际结果（bugs 组 5 / 22）

**执行方式**：每个用例起一个独立 Agent 会话，让它加载 ASCOS 后自然回应，人工按四个维度判分。

## 两个最关注的指标

| 指标 | 结果 | 依据 |
|---|---|---|
| **Evidence Discipline** | **5/5 达标** | 全部显式声明证据级别（均落 L2）；全部使用「疑似 / 最可能根因 / 待验证」；无一处出现「已定位 / 已修复 / 已验证」；每条结论带置信度与支撑证据 |
| **Unnecessary Question Rate** | **0 次阻塞式提问** | 5 例都向用户要了信息，但都明确「不等你，我先按假设顺序推进」。唯一申请批准的是**不可逆动作**（退款、生产 DDL、线上插桩、缩副本、补偿重跑）—— 这正是新规则要求的，不算多余提问 |

## 逐例要点

- **E14**：先指出「Node/TS 不会产生 NullPointerException」这个矛盾，把"去哪个服务查"当分叉点排除，再进假设。质量高于预期。
- **E15**：主动去查了微信支付官方回调重投时序（15s/15s/30s…最多 15 次），把"一个月几次"对上重投指纹。没有用"偶发"当借口跳过建环。
- **E16**：严格遵守"先测量后修"，用 EXPLAIN + `git bisect run` 而不是打日志；还主动指出「断言响应 <500ms 的测试必然 flaky」，改用查询次数作为 seam。
- **E17**：探针设计用 CDP `Performance.getMetrics` + 强制 GC 后读数，能区分真泄漏与 GC 假涨。
- **E22**：**规则改动验证通过** —— 自动降级到 L2、没有停住、没有申请"能否继续分析"的许可、没有改生产代码（只加只读观测与指标）、升级路径写清了「拿到 X → L1，能起 Testcontainers 注入固定 Clock → L0」。

## 本次执行的两个局限（会影响基线，必须记住）

1. **harness 屏蔽了文件与命令访问** —— 5 例因此**全部**落在 L2，无法区分"该给 L0 时给了 L0"和"该给 L0 却降级"。E14/E16/E17 本应拿 L0，这轮测不出来。
   → 下一轮必须在**真实项目 + 可执行命令**的环境跑，否则 bugs 组会全部塌缩到 L2。
2. **5 例全部是"无代码库上下文"的冷启动** —— 真实使用中 Agent 能读代码，行为会不同。

## 新发现（值得加进下一轮维度）

**输出体量偏大**。5 例回复都在 1500–2500 字，含大量表格。虽然内容质量高，但与 `non-negotiables` 第 3 条「输出自适应」存在张力 —— 一个中任务是否该输出这么长？
建议下一轮增加维度：**Output/Scale Fit（输出体量与任务规模是否匹配）**。目前不判 Fail，先只记录观察。
