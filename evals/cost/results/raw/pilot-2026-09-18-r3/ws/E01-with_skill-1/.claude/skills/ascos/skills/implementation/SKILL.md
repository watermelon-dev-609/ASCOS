# Implementation — 编码

写代码，并用**红-绿**循环保证写出来的东西真的能工作。

## 契约
- **输入**：补全后的需求 + 设计（来自 `requirements` / `architecture`）
- **输出**：可运行代码 + 测试 + 验证命令（Build / Test / Lint / Type Check）
- **失败状态**：无法在已明确的 seam 上测试 → 明确说明并记为风险，不得假装已验证

## 步骤

### 1. 加载本次要用的规范
按技术面加载：`references/frontend.md`、`backend.md`、`database.md`、`security.md`、`testing.md`。

### 2. 先明确 seam，再写测试
**动手前自己写下本次被测的公共边界（seam）；不穿透内部实现。**

seam 是**内部决策，不默认拿去问用户** —— 无条件确认会和「能合理推断就不狂问」冲突。
只在下列情况才询问：
- 是**公共 API / 跨服务契约**（改动会影响外部调用方）；
- 存在**多种合理方案**且选型会影响架构边界（此时回到 `architecture` 找词汇与判据）；
- 需要**新造一个 seam**（引入接口或抽象）才能测 —— 这本身是设计决策，必须说明理由，
  否则等于为测试凭空增加一层间接。

问自己："公共接口是什么？应该测哪些 seam？"

### 3. TDD 红绿循环（逻辑复杂或需高置信度时）
- **红先于绿**：先写失败测试，再写刚好让它通过的最小实现。不预想未来测试，不加投机特性。
- **一次一片（vertical slice）**：一个 seam、一个测试、一次最小实现为一轮。
- **重构不属于红绿循环**，归 `code-review` 阶段。

反模式：
- **实现耦合**：mock 内部协作者、测私有方法、绕过接口查库。判定信号：重构后行为没变但测试红了。
- **同义反复**：断言以代码同样的方式重算期望值（`expect(add(a,b)).toBe(a+b)`），构造上永远成立。期望值必须来自独立真值来源：已知正确字面量、手算样例、规格。
- **水平切片**：先写完全部测试再写实现 → 验证的是想象中的行为，对真实变更不敏感。

### 4. 编码纪律（硬约束）
高内聚低耦合 / SRP / KISS / DRY / YAGNI；业务与 IO 分离；所有外部输入校验；参数化查询防注入；鉴权 + 授权（**前端只控展示，权限只在后端校验**）；日志脱敏；幂等 / 事务 / 并发竞态；资源用完即释放。
完整清单见 `references/engineering-standards.md`。
前端额外：四态齐全（loading / 空 / 报错 / 无权限）、表单校验、提交防重复、弹窗支持 ESC 与点遮罩关闭。

### 5. 测试分级（按风险匹配深度，不一律最重）
- 核心业务：单元 + 集成，覆盖关键逻辑与边界。
- Bug 修复：优先补回归测试（见 `debugging`）。
- 权限 / 安全 / 支付 / 事务：必须测**异常路径与攻击路径**（越权、注入、并发冲突、重复提交）。
- 普通 UI 微调：按风险决定，低风险可仅冒烟。

### 6. 自检变更影响
对照 `references/change-impact.md` 复查：是否有未预料到的调用方、测试、文档需要同步。

## 输出
代码 + 测试 + **可复现的验证命令**（不是"应该没问题"）。命令与结果交给 `verification` 作为证据。

## 反模式
- 没跑过就声称"已实现"。
- 为了覆盖率测私有实现细节。
- 顺手大范围重构（与本次需求无关）。
- 引入新依赖不评估（见 `references/supply-chain.md`）。
