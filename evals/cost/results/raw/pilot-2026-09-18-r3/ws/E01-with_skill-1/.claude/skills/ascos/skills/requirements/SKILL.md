# Requirements — 需求补全

用户只说一点，不代表系统只有这一点。本 Skill 把一句话需求升级为可执行的需求集合，**主动补全而非狂问**。

## 契约
- **输入**：用户原话 + 代码库上下文（已有项目需先读 `CONTEXT.md`）
- **输出**：补全后的需求（含事实/假设/建议标注）+ 验收标准 + 风险点 + 待确认项（若有）
- **失败状态**：存在阻断性业务决策缺失 → 输出待确认项清单并**停止**，不进入实现

## 步骤

### 1. 对齐领域语言（已有项目）
读 `CONTEXT.md`（`references/context-model.md`）。用项目的真实术语命名概念；发现同物异名或用户用语与代码冲突时，先消歧再继续。无 `CONTEXT.md` 且概念已影响实现 → 建一个最小的。

### 2. 判断完整性
逐项检查用户没说但系统必需的部分：
- **边界**：空值、极值、长度上限、首/末项、分页。
- **异常**：非法输入、依赖失败、超时、并发冲突、部分失败。
- **状态**：非法 / 空 / 过期 / 越权状态如何处理。
- **权限**：谁能做这件事？对象级鉴权？前端展示 ≠ 后端校验。
- **安全**：注入、XSS、越权、脱敏、限流。
- **可观测**：失败怎么发现？日志脱敏了吗？
- **数据**：一致性要求、幂等、事务边界。
- **未来扩展**：哪些是现在不必做的（显式列为"不做"）。

### 3. 第一性原理
- 核心用户价值是什么？
- 最小必要能力集合是什么？
- 哪些不变量必须成立？
- 关键失败模式有哪些？

### 4. 对抗性审查
- 会怎么失败？怎么被滥用？
- 重试 / 并发 / 部分失败会怎样？
- 最容易被忽略的攻击面是什么？

### 5. 补全并三分标注
- **事实**：来自用户、代码或已验证来源。
- **假设**：为推进做的推断，**必须显式说明**。
- **建议**：基于工程判断的推荐。

### 6. 分叉点穷问（仅大任务）
以下任一项未定 → 停下来问用户，不要猜：
数据归属 / 权限模型 / 同步 vs 异步 / 是否多租户。
小中任务：直接选合理默认并标注为假设，不阻断。

### 7. 输出验收标准
可判定的条件，而非形容词。例："连续 5 次密码错误后锁定 15 分钟"而非"要安全"。

## 输出形态（按规模裁剪）
- **小**：补全点 2–5 条 + 风险，一句话带过。
- **中**：补全清单 + 验收标准 + 风险点（可写在交付说明里，不必单独 PRD）。
- **大**：完整 `templates/PRD.md`，并作为 `architecture` 的输入。

## 反模式
- 把"问用户"当偷懒：能推断的先推断并标注为假设。
- 补全到过度设计：只补系统必需的，不补"未来可能需要"的。
- 把推断写成事实：三分法不是形式，是防错。
- 需求变更时不更新下游（见 `references/artifact-continuity.md`）。
