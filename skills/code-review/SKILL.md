# Code Review — 双轴审查

交付前的 Code Review 不是"看一眼"，而是沿两个**互相独立**的轴审查，避免一个轴掩盖另一个。

- **Standards 轴**：代码是否遵循本仓库 / ASCOS 文档化的工程规范？
- **Spec 轴**：代码是否忠实实现了「补全后的需求」？

两轴**互相独立**地执行，最后并排汇报；**不要合并或重排**两轴结论（见末「为何双轴」）。
有 subagent 能力就并行；没有就串行两遍（见第 4 步 fallback）——**不是所有宿主都支持子代理**。

## 契约
- **输入**：对比基点（自动推断，推断不出才问）+ 规格来源
- **输出**：`## Standards` 与 `## Spec` 两份报告（**按严重度排序**）+ 一句话总结（每轴发现数 + 每轴最严重一项）
- **失败状态**：基点不可解析或 diff 为空 → **立即报错**，不要派发子代理

## 流程

### 1. 固定对比基点（**先自动推断，推断不出才问**）
按序尝试，取第一个可靠的：
1. 用户显式给出的基点（commit SHA / 分支 / tag / `HEAD~N`）。
2. 当前分支的 upstream：`git rev-parse --abbrev-ref --symbolic-full-name @{u}`。
3. 仓库默认分支：`git symbolic-ref refs/remotes/origin/HEAD`，取不到则看 `main` / `master` 是否存在。
4. 用 `git merge-base <候选> HEAD` 得到三点 diff 的基点。

全部失败（浅克隆 / 无 remote / 单分支无 upstream）→ 才询问用户。
确认 `git rev-parse <基点>` 可解析且 diff 非空，否则在此失败。
统一 diff 命令：`git diff <基点>...HEAD`（三点，针对 merge-base）；同时记录 `git log <基点>..HEAD --oneline`。

### 2. 确定 Spec 来源（按顺序）
1. 提交信息中的 issue 引用（`#123` / `Closes #45`）。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/`、`PRD.md`、`ADR.md` 或 `.scratch/` 下匹配分支 / 功能的规格文件。
4. 都没有 → 询问用户；若用户说没有规格，Spec 子代理跳过并报告「无规格」。

### 3. 确定 Standards 来源
仓库内任何定义"代码应如何写"的文件：`CODING_STANDARDS.md` / `CONTRIBUTING.md` / `CLAUDE.md` / `AGENTS.md` / ASCOS 的 `SKILL.md` 硬约束与 `references/`。

在此之上，Standards 轴始终携带下方**固定代码异味基线**（即便仓库什么都没写也适用，源自 Fowler《重构》ch.3）。两条约束：
- **仓库优先**：仓库已文档化的标准永远胜出；若它认可基线会标记的东西，压制该标记。
- **永远是判断，不是硬违规**：每条异味是带标签的启发式（「疑似 Feature Envy」），从不被当作硬违规；工具已强制的也跳过。

每条异味给出「是什么 → 怎么改」，对照 diff 匹配：
- **Mysterious Name** 名字不揭示用途 → 重命名。
- **Duplicated Code** 相同逻辑形状多处出现 → 抽成共享。
- **Feature Envy** 方法过度访问别的对象数据 → 把方法移过去。
- **Data Clumps** 几个字段总一起出现 → 包成一个类型。
- **Primitive Obsession** 原始类型 / 字符串代替领域概念 → 给概念自己的小类型。
- **Repeated Switches** 对同一类型的 switch/if 级联重复 → 多态或共享一张表。
- **Shotgun Surgery** 一处逻辑改动被迫散落多文件 → 聚合到一模块。
- **Divergent Change** 一个文件因多个无关原因被改 → 拆分。
- **Speculative Generality** 为需求没有的需要加的抽象 / 参数 / 钩子 → 删掉，内联回真实需要出现为止。
- **Message Chains** 长 `a.b().c().d()` 导航 → 在第一对象上藏起这趟行走。
- **Middle Man** 基本只转发 → 砍掉，直连真实目标。
- **Refused Bequest** 子类 / 实现者忽略或覆盖大部分继承 → 弃继承，用组合。

### 4. 派发两个子代理（**无 subagent 时走串行 fallback**）

**支持 subagent 的宿主** → 并行派发，互不污染上下文：
- **Standards 子代理**提示含：完整 diff 命令与提交列表、第 3 步找到的标准源文件 + 上面完整异味基线（子代理无其他访问途径）、简报：「按文件 / hunk 报告 (a) 每处违反文档化标准，引用标准（文件 + 规则）；(b) 任何基线异味，命名并引用 hunk。区分硬违规与判断：文档标准违反可硬，基线异味永远判断，仓库标准压过基线。工具已强制的跳过。**按第 4.1 节严重度排序输出**。400 词内。」
- **Spec 子代理**提示含：diff 命令与提交列表、规格路径或内容、简报：「报告 (a) 规格要求缺失 / 部分；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似实现但实现疑似错误的需求。每条引用规格原文。**按第 4.1 节严重度排序输出**。400 词内。」

**不支持 subagent 的宿主** → 串行两遍，关键是**第二遍开始前清掉第一遍的结论**：
1. 先跑 Standards 轴，写完 `## Standards`；
2. 重置上下文（新会话，或显式声明「忽略上一轮结论，独立重新审查」）后再跑 Spec 轴；
3. 两遍都不得回头修改另一轴的结论。

> 串行 fallback 要防的唯一风险是**锚定**：第一轴的结论渗入第二轴。
> 若宿主无法真正隔离上下文，就在报告里显式标注
> 「两轴串行执行，Spec 轴可能受 Standards 轴锚定影响」—— 不要假装它和并行等价。

规格缺失则跳过 Spec 轴并在报告中注明。

### 4.1 严重度排序（defect-first）
两轴内部都按此顺序输出。**先报缺陷，再报可维护性**：

| 级别 | 含义 |
|---|---|
| 1 **Blocking** | 正确性或安全缺陷：会导致线上错误、数据损坏、越权 |
| 2 **Regression** | 本次改动引入的行为回退 |
| 3 **Spec miss** | 需求未实现或实现错误 |
| 4 **Maintainability** | 结构性、可读性、重复 |
| 5 **Smell** | 上面那份 Fowler 异味基线（永远是判断，不是硬违规） |

每轴**先列 Blocking / Regression**，异味放最后。
理由：固定携带一整套异味基线，很容易产出"可维护性建议很多、真正的 Bug 被淹没"的报告。

### 5. 聚合
在 `## Standards` 与 `## Spec` 标题下并排呈现两份报告（逐字或轻微清理）。**不要合并或重排**结论。
末行一句话总结：每轴发现数 + 每轴最严重一项（若有）。**不要跨轴选唯一冠军**：那正是分离要防止的重排。

## 为何双轴
一次改动可以过一轴败一轴：
- 每一条标准都遵守，但实现了错误的东西 → **Standards 过，Spec 败**。
- 完全按需求实现，却破坏了项目约定 → **Spec 过，Standards 败**。

分开汇报，防止一轴掩盖另一轴。
