# Architecture — 架构与接口设计

设计**深模块**：小接口后面藏大量行为，放在干净的 seam 上，且能通过该接口测试。

## 契约
- **输入**：补全后的需求（来自 `requirements`）+ 代码库感知结论
- **输出**：模块与接口设计 + 变更影响清单 + ADR（重大决策时）+ 待定项
- **失败状态**：需求不足以确定边界 → 退回 `requirements`

## 词汇（统一使用，不要替换成"组件/服务/边界"）
| 术语 | 含义 |
|---|---|
| **Module** | 任何有接口与实现的东西：函数、类、包、跨层切片 |
| **Interface** | 调用方正确使用所必须知道的一切：签名、不变量、顺序约束、错误模式、性能特征 |
| **Seam** | 可以不在此处编辑就改变行为的位置；即接口所在之处 |
| **Adapter** | 在 seam 上满足接口的具体实现（Postgres repo、内存 fake） |
| **Depth** | 接口的杠杆：调用方每学一单位接口能行使多少行为 |
| **Leverage / Locality** | 调用方得到的复用收益 / 维护者得到的变更局部性 |

## 三条硬判据（反过度设计从口号变可执行）
1. **删除测试**：删掉这个模块，复杂度随之消失 → 它是透传层，删掉。复杂度在 N 个调用方重新出现 → 它真的在创造价值。
   **边界**：只适用于**已经存在的模块**。为需求引入的新模块，删除测试必然通过（删了就没人调用），
   此时改用第 2、3 条判定 —— 新模块必须有**已经存在的第二个实现或第二个调用方**，
   否则先写成函数，等出现第二个调用点再抽。
2. **接口即测试面**：调用方和测试跨过同一个 seam。如果你总想"测过接口"，模块形状多半错了。
3. **一个 adapter 是假 seam，两个才是真 seam**：没有东西在变化，就不要引入接缝。这条直接对应 YAGNI。
   **边界**：这条判断的是「**抽象**是否成立」，不判断「**封装**是否有价值」。
   把 200 行函数按职责拆成 3 个私有函数、把重复的 20 行抽成 helper —— 这些不产生新接口，
   目的是降低认知负担，**不需要**满足"两个实现"。
   只有当你准备新建一个**调用方必须知道的对外接口/抽象**时，才适用这条。

## 设计步骤
1. **定 seam**：行为在哪里需要可替换 / 可测试？先定位置，再定背后放什么。
2. **定接口**：能减少方法数吗？能简化参数吗？能往里藏更多复杂度吗？
3. **定数据**：实体、关系、一致性要求、迁移路径（读 `references/database.md`）。
4. **定错误表达**：统一错误契约（Web 场景示范：`{ ok, code, msg, data }`；非 Web 栈按栈适配，保留"统一错误表达"原则即可）。
5. **变更影响分析**（`references/change-impact.md`）：API / 数据字段 / 权限 / 公共组件 / 配置五类逐一过，输出受影响清单 + 兼容性结论 + 需同步的测试与文档。
6. **记录 ADR**：重大决策用 `templates/ADR.md` 写背景、决策、备选、后果。

## 默认选更简单的一侧（除非需求明确要求）
单体 > 服务拆分；同步 > 异步；关系型 > NoSQL；直查 > 缓存；成熟库 > 自建。
引入任何基础设施（MQ / Redis / K8s / 向量库）必须在交付里写明**收益**（解决什么具体问题）+ **成本**（运维、复杂度、学习曲线）。

## 技术栈适配
`controller/service/repository`、`{ ok, code, msg, data }` 是 **Web 后台的原则性示范**。CLI、数据管道、ML、移动端、嵌入式等场景：保留原则（契约先行、输入校验、业务/IO 分离、统一错误表达、可观测、测试三场景），不必照搬分层。

## 输出形态
- **中任务**：设计要点 + 变更影响清单（可写在交付说明里）。
- **大任务**：完整设计 + ADR + 接口规格（`templates/API_SPEC.md`）。

## 反模式
- 先建抽象再找第二个实现（假 seam）。
- 为"以后可能要"预留扩展点、参数、钩子。
- 用分层数量证明架构严谨（浅模块堆砌）。
- 变更影响只扫自己要改的文件。
