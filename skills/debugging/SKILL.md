# Debugging — 系统化调试

**反馈环就是本 Skill。** 有一个"能在这一个 bug 上变红"的紧信号，你一定会找到原因；没有它，盯着代码看多久都救不了你。

## 契约
- **输入**：缺陷现象 + 环境信息（已有项目需先读 `CONTEXT.md` 拿到模块心智模型）
- **输出**：根因 + 最小修复 + 回归测试 + 复测结论
- **失败状态**：**无法构建反馈环 → 停止，不要进入假设阶段。** 说明已尝试的方法，向用户索取：可复现环境、脱敏的捕获产物（HAR / 日志 / core dump / 带时间戳录屏），或临时线上插桩许可。

## 脱敏前置
本 Skill 会展示命令、输出与产物。**任何密钥先替换为 `<REDACTED>`**；循环基于环境变量构建，让凭证留在环境里而不是出现在你展示的内容中。捕获产物常带 auth header：只引用携带信号的那几行。

## Phase 1 · 构建反馈环
按大致顺序尝试：
1. 失败测试（单元 / 集成 / e2e，能触达该 bug 的 seam）
2. curl / HTTP 脚本打开发服务器
3. CLI 调用 + fixture 输入，stdout 与已知正确快照 diff
4. 无头浏览器脚本（Playwright / Puppeteer）驱动 UI 并断言 DOM / console / network
5. 重放捕获的 trace（请求、payload、事件日志落盘后隔离重放）
6. 一次性 harness（起最小子集、mock 依赖，一次函数调用命中 bug 路径）
7. 属性 / 模糊测试（"偶尔输出错" → 跑 1000 个随机输入找失败模式）
8. 二分 harness（bug 出现在两个已知状态之间 → 自动化"在状态 X 启动并校验"以便 `git bisect run`）
9. 差分循环（同一输入跑旧版 vs 新版，diff 输出）
10. 人工 bash 循环（最后手段：必须人点击时，用脚本驱动人，保持循环结构化）

**把循环当产品来打磨**：能更快吗？（缓存 setup、跳过无关初始化、收窄测试范围）信号更锋利吗？（断言具体症状，而非"没崩"）更确定吗？（固定时间、播种随机、隔离文件系统与网络）
30 秒但 flaky 的循环几乎等于没有；2 秒且确定的是调试超能力。

**非确定性 bug**：目标不是干净复现，而是**更高的复现率**。循环触发 100 次、并行化、加压、注入 sleep。50% 可调试，1% 不可。

### 完成判据：一条能变红的紧命令
Phase 1 结束的标志是你能说出**一条命令**（脚本路径 / 测试命令 / curl），**且你已经跑过至少一次**（展示调用与脱敏后的输出），并满足：
- [ ] **可变红**：驱动真正的 bug 路径，断言**用户的确切症状**，修好后能变绿
- [ ] **确定性**：每次判定一致（flaky 则固定为高复现率）
- [ ] **快**：秒级，不是分钟级
- [ ] **可无人值守**：你一个人能跑；需要人时走结构化脚本

如果你发现自己在这条命令存在之前就读代码构建理论 —— **停下**。直接跳到假设，正是本 Skill 要防的失败。

## Phase 2 · 复现并最小化
- [ ] 产生的失败模式是**用户描述的那个**，不是恰好在附近的另一个（修错 bug = 白修）。
- [ ] 多次运行可复现（或非确定性 bug 达到可调试的高复现率）。
- [ ] 已捕获确切症状（错误信息、错误输出、慢的耗时），供后续验证修复是否对症。

**最小化**：一次砍掉一个输入 / 调用方 / 配置 / 数据 / 步骤，每次砍完重跑循环，只保留对失败**承重**的部分。
完成判据：**剩下每个元素都是承重的** —— 去掉任何一个，循环就变绿。
最小化后的 repro 同时是 Phase 5 的干净回归测试。

## Phase 3 · 假设
**先生成 3–5 个带排序的假设，再开始验证任何一个。** 单假设生成会锚定在第一个看起来合理的想法上。
每个假设必须**可证伪**，格式：
> "如果 X 是原因，那么改变 Y 会让 bug 消失 / 改变 Z 会让 bug 加重。"

说不出预测的就是 vibe， sharpen 或丢弃。
**把排序后的清单给用户看一眼再动手** —— 他们常有能瞬间重排的领域知识（"我们刚上了 #3 的改动"）。这是便宜的检查点，不要阻塞：用户不在就按自己的排序推进。

## Phase 4 · 插桩
每个探针映射到 Phase 3 的某条具体预测，**一次只改一个变量**。
工具优先级：调试器 / REPL 断点 > 边界上的定向日志 >> 打满日志再 grep。
**每条调试日志打唯一前缀**（如 `[DEBUG-a4f2]`），收尾时一次 grep 清干净。没打标签的日志会长期存活。
**性能回退分支**：日志通常没用。先建基线测量（计时 harness / profiler / 查询计划），再二分。**先测量，后修。**

## Phase 5 · 修复 + 回归测试
**先写回归测试，再修**，但只在存在**正确 seam** 时写。
正确 seam = 测试能在调用点复现**真实的 bug 模式**。若唯一可用的 seam 太浅（单调用方测试，而 bug 需要多调用方；单元测试无法复现触发链），在那里的回归测试只会带来虚假信心。
**没有正确 seam 本身就是发现**：说明代码库架构在阻止你锁死这个 bug，记为风险并上报。

有正确 seam 时：
1. 把最小化后的 repro 变成该 seam 上的失败测试。
2. 看它红。
3. 应用修复。
4. 看它绿。
5. 对**未最小化**的原始场景重跑 Phase 1 的反馈环。

## Phase 6 · 清理（声明完成前必做）
- [ ] 原始场景不再复现（重跑 Phase 1 循环）
- [ ] 回归测试通过（或无 seam 的情况已记录）
- [ ] 所有 `[DEBUG-…]` 插桩已移除（grep 该前缀）
- [ ] 一次性原型已删除或移到明确标记的调试目录
- [ ] **被证实的那条假设写进 commit / PR 说明**，让下一个调试者能学到

## 反模式
- 不看日志直接改代码猜位置。
- 只屏蔽报错、不解决根因。
- 顺手大范围重构导致新回归。
- 无反馈环就靠"感觉"定位。
